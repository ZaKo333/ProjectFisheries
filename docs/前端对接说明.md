# 前端对接说明（交给页面设计方）

> 面向：重新设计演示页的同学。
> 目的：说清**后端已经实现了什么、前端能从哪拿到、哪些东西不能由前端自己算**。
> 项目名 **ProjectFisheries**：淡水池塘养殖的病害与水质风险智能体。
> 代码根目录 `project/`（本文所有相对路径都相对它）。

---

## 0. 先看这三句话

1. **后端已经全部做完**，前端只需要"把已有的字段排布出来"，不需要实现任何业务逻辑。
2. **风险等级、风险分、告警内容一律由后端规则算出**，前端只负责显示。前端一旦自己算分，就会出现"页面上的数字和报告里的数字对不上"，这是这类系统最容易被问倒的地方。
3. **有两条对接路线**：HTTP 接口（推荐，语言无关）或直接 import Python 层。两条路线给的是**同一批字段**。

## 1. 两条对接路线

### 路线 A（推荐）：HTTP 接口

```powershell
cd D:\设置\项目\Agent\project
.\.venv\Scripts\python.exe -m fisheries.api
# → http://127.0.0.1:8000        Swagger 交互文档：http://127.0.0.1:8000/docs
# → OpenAPI 规范（可直接生成 TS/Java 客户端）：http://127.0.0.1:8000/openapi.json
```

- 优点：语言无关；打开 `/docs` 就能点着试；`/openapi.json` 可以喂给 `openapi-generator` 直接生成类型定义。
- 全部接口在 `/api/v1` 下，跨域已默认开启（`FISHERIES_API_ENABLE_CORS=1`）。
- **`/docs` 是给设计同学最好的说明书**，字段名、类型、必填与否、示例值都在里面。

### 路线 B：Python 内嵌（新前端也是 Python 时用）

```python
from fisheries.webui import WebRequest, WebSession

session = WebSession(use_knowledge=True)      # 启动时加载向量库，约 1 秒
result = session.run(WebRequest(
    readings=[...],          # list[dict]，见 §3.1
    image_path=None,         # 服务器本地路径，可选
    pond_id="demo-pond-1",
    species="鲤科",           # 鲤科 / 罗非鱼 / 虾蟹
    question="",
    mock_source="hash",      # hash / folder_hint
    use_knowledge=True,
))
print(result.risk_level, result.fused_score, result.headline)
```

`WebResult` 的字段与 HTTP 响应**一一对应**（见 §3.3）。

> ⚠️ **必须串行调用 `session.run()`**。`AquacultureAgent` 内部会复用
> `self.trace` / `self.degraded_reasons` / `self.translation_notes`，
> 实例不是线程安全的。`WebSession` 里已内置 `run_lock`，用 HTTP 接口时
> `AppState` 也加了锁——**新前端若自己起线程池，必须自己保证串行**。

### 路线 C：保留现有页面骨架，只换渲染层

现有 Gradio 页面在 `src/fisheries/webui/`，其中 `render.py` **不依赖 Gradio**
（纯字符串渲染，返回 Markdown 或 HTML 片段）。可以直接复用它的信息排序，
只替换外层容器：

| 函数 | 返回 | 内容 |
|---|---|---|
| `render_summary_markdown(result)` | Markdown | 顶部大结论（等级 + 分数 + 主控因子 + 一句话理由） |
| `render_alerts(result)` | HTML | 告警卡片（按 critical > warning > info 排序，带配色） |
| `render_report(result)` | Markdown | 处置建议主体：水质调控 / 病害处置 / 观察窗口 / 可信度 |
| `render_data_quality(result)` | Markdown | 表格接入质量（点数、间隔、缺失、丢弃行） |
| `render_vision(result)` | Markdown | 鱼体图片识别结果（病种、置信度、是否需复核） |
| `render_fusion(result)` | Markdown | 融合依据（加权公式值 / 等级下限 / 权重 / 协同 / 模态） |
| `render_trace(result)` | Markdown | 推理链路（调度 → 工具 → 融合 → 建议） |
| `render_knowledge(result)` | Markdown | 知识库引用（带「依据 GB 11607-1989；核验日期 2026-10-15」，未核验的仍标"未与标准原文核对"） |
| `render_status(result)` | Markdown | 后端状态（LLM 后端、降级原因、耗时） |
| `render_error(message)` | HTML | 错误卡片（已做 HTML 转义） |

**契约**：所有 `render_*(result)` 在 `result.ok == False` 时返回空串，
失败时只显示 `render_error(result.error)` 一个卡片。

## 3. 核心端点 `POST /api/v1/assess`

### 3.1 请求

```json
{
  "pond_id": "demo-pond-1",
  "species": "鲤科",
  "readings": [
    {"timestamp": "2026-10-13T08:00:00", "water_temp": 27.4, "ph": 7.85,
     "dissolved_oxygen": 6.42, "ammonia_n": 0.100, "nitrite_n": 0.050}
  ],
  "image_path": null,
  "upload_id": null,
  "mock_source": "hash",
  "use_knowledge": null,
  "question": "明天早上要不要提前开增氧机？",
  "include_trace": true,
  "include_knowledge_block": true
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pond_id` | str | ✗ | 池塘编号，默认 `unknown`。前端应让用户填 |
| `species` | `鲤科` \| `罗非鱼` \| `虾蟹` | ✗ | **决定阈值档位**，不是显示用的。默认 `鲤科` |
| `readings` | list | ✗ | 至少 3 条，按时间升序。**`water_temp` / `ph` / `dissolved_oxygen` / `ammonia_n` 四个字段必填**，`timestamp` 与 `nitrite_n` 可选 |
| `image_path` | str | ✗ | 服务器本地路径（生产应关闭）。**前端应走 `upload_id`** |
| `upload_id` | str | ✗ | 先调 `/ingest/image` 拿 |
| `mock_source` | `hash` \| `folder_hint` | ✗ | 仅 YOLO 未训练时生效。演示用 `folder_hint` 更稳定 |
| `use_knowledge` | bool \| null | ✗ | 是否做 RAG 检索，null = 服务端默认 |
| `question` | str | ✗ | 自然语言补充问题（≤500 字） |
| `include_trace` | bool | ✗ | 是否返回推理轨迹（默认 true） |
| `include_knowledge_block` | bool | ✗ | 是否返回注入提示词的知识原文（默认 true） |

**约束（前端要替用户挡住）**：

- `readings` 与 `image_path`/`upload_id` **至少要给一个**，否则 422；
- `readings` 传了空数组会 422（"二者给一个" ≠ "传个空表"）；
- 所有模型 `extra="forbid"`：字段名拼错会**报错**而不是静默忽略——这是刻意的，
  拼成 `dissolved_oxyen` 应该 422，而不是算出一个"没有溶氧的风险分"；
- **时间戳要么全给要么全不给**。时间戳决定采样间隔推断与"外推几小时"的含义；
  只有一部分带时间戳时，后端会整份退回按"请求里给的间隔"处理。

### 3.2 响应字段（按前端使用频率排序）

| 字段 | 类型 | 前端怎么用 |
|---|---|---|
| `risk_level` | `正常` \| `预警` \| `高危` | 顶部最显眼的位置。**只有这三个值** |
| `fused_score` | float 0–100 | 大号数字。**这是判级所依据的分数** |
| `headline` | str | 一句话结论（已含【高危】前缀），建议做成标题下第一行 |
| `reason` | str | 为什么是这个等级（含权重与等级下限说明），做"为什么"折叠区 |
| `report` | object | **面向养殖户的完整报告**，见 §3.3 |
| `alerts` | list | 告警卡片，见 §4.2 |
| `evidence` | list | 证据链（指标、阈值、数值），做"判定依据" |
| `water` | object | 水质工具原始返回（含 `trends` / `projections` / `data_quality`） |
| `vision` | object | 图片识别原始返回（`null` = 没传图片） |
| `fusion` | object | 融合层结构化结果，见 §4.3 |
| `references` | list[str] | 知识库引用，形如 `《文件名》> 标题 > 子标题（未核对标准原文）` |
| `knowledge_summary` | object | `{backend, n_chunks, degraded, warnings, purposes}` |
| `knowledge_block` | str | 实际注入提示词的资料原文（给评委看"确实接了 RAG"） |
| `trace` | list | 推理轨迹，见 §4.4 |
| `llm_backends` | object | `{scheduler: "...", advisor: "..."}` |
| `degraded_mode` | bool | **页面必须显示**，见 §5.2 |
| `degraded_reasons` | list[str] | 降级原因，人话，直接可显示 |
| `elapsed_seconds` | float | 耗时 |
| `advisories` | list | 展平后的建议（兼容旧前端），**新前端用 `report`** |
| `observation_window` / `confidence_note` | str | 从 `report` 展平出来，同上 |

### 3.3 `report` 对象（建议直接用这个）

```json
{
  "risk_level": "高危",
  "headline": "【高危】溶氧出问题了，马上处理。",
  "alerts": [{"code": "DO_REDLINE_PROJECTED", "level": "critical",
              "title": "水质红线告警", "detail": "..."}],
  "water_actions":   [{"priority": 1, "target": "溶氧快跌破泛塘线",
                       "action": "全部增氧机马上开，停料，换掉 1/3 水，撒增氧剂。",
                       "timing": "立刻做，至少守 6 小时"}],
  "disease_actions": [],
  "observation_window": "6 小时后复测溶氧和氨氮，明天看鱼有没有好转。",
  "confidence_note": "依据：水质 24 点。不确定：结论含 12.0 小时外推；水质工具处于降级模式等。复核：建议人工核对水质原始数据。"
}
```

- **`water_actions` 与 `disease_actions` 必须分成两个视觉区块**。两块的读者动作完全不同：水质块是"今晚就要动手"（开增氧机、换水），病害块是"隔离、用药、停药期"。混在一起养殖户会执行错顺序。
- `priority` 是 1 起的整数，**同一块内按它排序**（后端也按 `(priority, target)` 排好了，前端照序渲染即可）。
- `target` / `action` / `timing` 是三段固定结构，建议 `target` 做小标题、`action` 做正文、`timing` 做右侧标签。`timing` 经常含具体时刻（"1.9 小时后会掉到 1.5，之前必须开机"），别截断。
- `observation_window` 是**复查动作**，且它跟着风险来源走（水质异常 → 复测溶氧；查出病害 → 每天捞死鱼记数）。
- `confidence_note` 是固定三句式（`依据：…。不确定：…。复核：…。`），**不要把三个分句拆开或重排**——它的价值在于结构固定、一眼可比。

### 3.4 一个真实的预警样例（注意：`alerts` 是空数组）

```json
{
  "risk_level": "预警",
  "fused_score": 57.07,
  "reason": "融合分 57.1（水质模态 0.57×1.00），判定等级【预警】，本次仅有水质单模态输入，权重已归一化；等级下限 WATER_LEVEL:预警。",
  "alerts": []
}
```

⚠️ **设计要点**：`预警` 时 `alerts` 完全可能为空（这次没有触发任何"红线/告警"模板，
是**分数**把它推过了 40 分线）。所以**告警面板不能是风险的唯一载体**——
顶部等级色块 + `fused_score` + `reason` 必须独立可见，否则会出现
"页面显示没有告警，但等级写着预警"的观感矛盾。

## 4. 五个必须看懂的数据结构

### 4.1 风险等级只有三档

`正常` / `预警` / `高危`。定级由后端规则算出，**六条规则可能同时命中**，前端不需要理解优先级，只需要展示最终结果与 `reason`。

### 4.2 `alerts[]`

| 字段 | 说明 |
|---|---|
| `code` | 机器标识，如 `DO_REDLINE_PROJECTED`、`SEVERE_DISEASE`、`LEVEL_FLOOR` |
| `level` | `critical` / `warning` / `info` |
| `title` | 短标题（"水质红线告警"） |
| `detail` | 详情 |

建议配色：`critical` 红、`warning` 橙、`info` 蓝。`LEVEL_FLOOR` 这条比较特殊，
它的含义是"**加权公式算出的分数不够高，是等级下限把它抬上来的**"，
detail 里会写明原值和抬升后的值。

### 4.3 `fusion` 对象（做"融合依据"面板用）

| 字段 | 含义 |
|---|---|
| `fused_score` | 最终判级依据的分数 |
| `weighted_score` | **纯加权公式值**（含协同加成），保留给审计 |
| `score_floor` | 被下限抬升到的分数，`null` = 没被抬升 |
| `level_floors` | 触发了哪些下限，如 `["REDLINE","WATER_LEVEL:高危"]` |
| `water_score` / `vision_score` | 两个模态各自的 0–1 严重度 |
| `effective_weights` | 实际生效权重，如 `{"water":0.6,"vision":0.4}`；单模态时归一化为 `{"water":1.0}` |
| `synergy_score` / `synergy_hits` | 协同加成与命中的规则 |
| `modalities` / `failed_modalities` | 参与了哪些模态 / 哪个失效了 |

**展示建议**：把 `weighted_score → fused_score` 的抬升过程显示出来
（例如 `32.3 → 70.0（等级下限 SEVERE_DISEASE）`）。这是整个系统最经得起追问的
设计点：**"照片上鱼看着还行"不能把水质高危稀释成预警**。

### 4.4 `trace[]`（推理轨迹，做成时间轴最好看）

| 字段 | 说明 |
|---|---|
| `step` | 序号 |
| `kind` | `llm` / `tool_call` / `tool_result` / `guardrail` / `fusion` / `advisor` / `error` |
| `title` / `detail` | 人话描述 |
| `data` | 结构化数据 |

`guardrail` kind 的含义：**大模型漏调了工具，护栏替它补调了**，并且不隐瞒。

### 4.5 `water` 对象里前端会用到的

| 字段 | 说明 |
|---|---|
| `trends.{indicator}.current/direction` | 各指标当前值与走向 |
| `projections` | 未来 12/24/48/72 小时的外推值 |
| `projected_do_alert_eta_hours` | "预计 N 小时后溶氧跌破 3.0" —— **这是最有说服力的一个数字** |
| `limiting_factor` / `limiting_factor_label` | 主控因子（英文键 / 中文名） |
| `data_quality` | `n_points` / `interval_minutes` / `interval_source` / `span_hours` / `missing_indicators` / `warnings` |
| `exceeded_indicators` / `rule_hits` / `redline_hits` / `severity_map` | 判定细节 |

### 5.2 三个**必须原样显示**的状态（不做成"高级设置里的小字"）

1. **`degraded_mode` + `degraded_reasons`**
   例：`未配置建议 LLM，养殖建议由规则模板生成`。
   这不是免责声明，是事实说明——评委一定会问"这是模型写的还是规则写的"，
   页面必须能直接回答。
2. **`llm_backends`**
   例：`scheduler: MockLLM（确定性离线模式）`。演示环境不连大模型是常态，
   说清楚比藏起来好。
3. **知识条目的 `（未核对标准原文）`**
   `references` 里已经带了后缀。行业标准原文目前是扫描件、无法自动提取，
   所以语料里有一部分是自编的。**这个标注不能过滤掉**——它是这个项目可信度的一部分。

### 5.3 输入侧的校验（前端应实现，避免用户看到 422）

| 校验 | 提示文案建议 |
|---|---|
| 表格 ≥ 3 行有效数据 | "水质趋势至少要 3 个点" |

| 时间戳全有或全无 | "这批数据里只有一部分行有时间，请补齐或全部删掉时间列" |
| 至少给一个模态 | "请上传水质表格或鱼体图片，两者给一个就能跑" |

> 现有的 `table.py` 已经能识别列名并给出上面这些提示，如果新前端是 Python 的，

> （它们不依赖 Gradio）。

## 6. 我的建议

### 6.1 信息架构：一张页面，从上到下一屏说完全部结论

评委的注意力只有几十秒。建议顺序（这也是现有页面验证过的顺序）：

```
① 顶部大结论条   等级色块 + 融合分 + 主控因子 + headline
② 告警面板       红/橙/蓝卡片；为空时显示"本次无告警，风险来自趋势外推"
③ 处置建议       ★ 默认展开。水质块 / 病害块两个分区
④ 观察窗口 + 可信度说明（三句式，整段显示不要拆）
⑤ 数据接入质量   （折叠）这张表读进去多少、丢了哪些行
⑥ 图片识别结果   （折叠）病种 + 置信度 + 是否需人工复核
⑦ 融合依据       （折叠）加权公式值 → 融合分，等级下限，权重
⑧ 知识库引用     （折叠）资料标题 + 未核对标注
⑨ 推理链路       （折叠）时间轴
⑩ 后端状态       （折叠）LLM 后端 / 降级原因 / 耗时
```

**① 到 ④ 必须不需要任何点击就能看到。** ⑨ 是"能自证"的关键（它证明这不是
一次 prompt 调用，而是"调度 → 工具 → 融合 → 建议"完整链路），但它不该占用首屏。

### 6.2 视觉建议

- **等级配色只有三套**：`高危` 红 `#c0392b` / `预警` 橙 `#d9822b` / `正常` 绿 `#1e8449`。
  现有实现用的就是这三个值，可以直接抄。
- **分数与等级永远同框**。历史上出现过"高危 / 32.3 分"这种自相矛盾的报告，
  现在后端已经保证分数不低于等级分数线，但前端仍应把两者放一起，
  一旦将来出现不一致，一眼就能发现。
- **`fused_score` 建议做成进度条**，并在 40 / 70 处画刻度线（这两个是预警/高危的分数线）。
- **告警卡片不要合并成一条**。每条 `code` 对应一个具体的处置理由，合并就丢信息了。
- **`reason` 字段是长句**，适合放"为什么判这个等级"的折叠区，不适合做副标题。

### 6.3 不要做的事（这几条踩过一次就会出问题）

1. **不要在前端重算风险分或重新定级。** 一个数字都不能自己算。
2. **不要按 `fused_score` 自己判断等级。** 后端有"等级下限"机制——
   分数 32.3 也可能是高危（因为检出了高致病性病害）。等级只读 `risk_level`。
3. **不要把两个模态的分数加权平均。** 后端刻意不这么做：
   水质高危 + 照片上鱼看着正常 ≠ 风险减半，只是"还没出现症状"。
4. **不要在图片分析失败时静默变成单模态。** `failed_modalities` 与
   `degraded_reasons` 会写明，页面必须显示"本次结论不含图像证据"。
5. **不要过滤 `（未核对标准原文）` 标注**（见 §5.2）。
6. **不要自己调 LLM 生成建议文案。** 后端有护栏：模型复述的等级与融合层不一致时
   整份输出作废。前端另起一套就绕过了这个护栏。
7. **不要给 `readings` 传空数组或部分带时间戳的序列**（见 §3.1）。

### 6.4 如果要做"趋势图"

`water.trends` 与 `water.projections` 里已经有 12/24/48/72 小时的外推值，
`GET /ponds/{pond_id}/history` 有历史评估记录。但**建议先不做图**：
现在用一句话说清了同样的事——「预计 12.6 小时后溶氧跌破 3.0 mg/L」——
比一条曲线更快被看懂，而且不会在手机上糊掉。真要做，至少要把
"外推点"与"实测点"在视觉上分开，否则等于把预测值当成实测值展示。
