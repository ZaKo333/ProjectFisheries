# 数据集说明

本文档盘点 ProjectFisheries 使用的全部数据资产：来源、规模、字段、类别定义、
**已实测的质量缺陷**，以及在本项目中的使用方式与弃用理由。

> 全部数字均为**在本地数据集目录上实测统计**得出，非来自数据集发布页的说明文字。

## 0. 数据在哪里——工程**不自带**数据集

数据集的「名字 → 位置」只在 **`src/fisheries/datasets.py` 的注册表**里定义一次，
其余代码一律通过 `fisheries.datasets.require()` / `resolve()` 取路径。
改造前那种把 `<工程上级>\数据集\...` 硬编码进 13 个文件的做法已经清零，
并有单元测试守着（`tests/unit/test_datasets.py`，禁止 `src/`、`scripts/`、`tests/`
里再出现字面量路径）。

**解析顺序**（先命中先返回）：

| # | 位置 | 说明 |
|---|---|---|
| 1 | 环境变量 `FISHERIES_DATA_ROOT` | 指向数据集**总目录**，每个数据集是它下面的一个子路径 |
| 2 | 工程内 `data/datasets/<entry>` | 本工程自带的导入落点 |
| 3 | 历史目录 `<工程上级>/数据集/<entry>` | 改造前就摆好的那份，**改造后照样找得到** |
| 4 | `data/dataset_index.json` | `fetch` 下载成功后自动记录，把 kagglehub 缓存里的绝对路径钉下来 |
| 5 | kagglehub 缓存 `~/.cache/kagglehub/...` | 只读扫描、不联网；本机已有缓存时无需再下载 |

> ⚠ **`FISHERIES_DATA_ROOT` 是「最优先的搜索位置」，不是「唯一位置」。**
> 它没命中时会继续往下找（所以本机那份历史数据仍然会被用上）。
> 想验证「数据缺失时会发生什么」，要连同历史目录一起挪走，或看
> `tests/unit/test_datasets.py::TestNotFound`。

全都没命中就抛 `DatasetNotFoundError`（继承 `FileNotFoundError`，老代码的
`except FileNotFoundError` 不用改一行），错误信息里**直接给出可复制的下载命令
和 `FISHERIES_DATA_ROOT` 的用法**——不会只说一句「找不到」。

### 0.1 体检与导入

```powershell
cd <工程>

.\.venv\Scripts\python.exe scripts\fetch_datasets.py --list     # 注册表里有什么
.\.venv\Scripts\python.exe scripts\fetch_datasets.py --status   # 本机有哪些（默认动作）
.\.venv\Scripts\python.exe scripts\fetch_datasets.py --where aquaponics_pond   # 只打印路径，供脚本调用
.\.venv\Scripts\python.exe scripts\fetch_datasets.py --status --size    # 附带体积（慢）
.\.venv\Scripts\python.exe scripts\fetch_datasets.py --status --json    # 机器可读

.\.venv\Scripts\python.exe -m pip install -e ".[datasets]"      # 装 kagglehub（可选依赖）
.\.venv\Scripts\python.exe scripts\fetch_datasets.py --fetch fish_disease
.\.venv\Scripts\python.exe scripts\fetch_datasets.py --fetch all
```

本机实测：**可用 13/14**（只有 `fish_disease_cleaned` 缺失，工程未使用它）。
`fish_species_images` 已导入，但它是**海洋礁鱼**、与本地养殖品种不重合，
鱼种训练改用 §2.9 的 `fish_species_freshwater`。kagglehub **未安装**：只有真去
`--fetch` 才需要它，离线部署与纯推理不需要。

#### 没有 Kaggle 凭证：走自建镜像（2026-10-17 新增）

`fetch` 现在是两条路：**先 kaggle，失败自动切镜像**，任意一条通就行。镜像不需要
任何凭证，只要一个能放静态文件的地址。

```powershell
# 打包（在已经把数据导好的机器上跑）
.\.venv\Scripts\python.exe scripts\pack_dataset_mirror.py --all          # 全部可打包的
.\.venv\Scripts\python.exe scripts\pack_dataset_mirror.py --name fish_disease --out dist\share
#   → dist\share\fish_disease.zip + manifest.json（内含每个包的 sha256）

# 上传：把 dist\share 整个目录放上去，确认 https://你的地址/manifest.json 能直接打开

# 换机器下载
$env:FISHERIES_DATASET_MIRROR = "https://你的地址/fish-datasets"
.\.venv\Scripts\python.exe scripts\fetch_datasets.py --fetch all
# 或一步到位：一键配置环境.bat --dataset-mirror https://你的地址/fish-datasets
```

三条工程约束（都由 `tests/unit/test_dataset_mirror.py` 的 19 项钉住）：

1. **字节可复现**：zip 内时间戳固定为 1980-01-01，同一份数据重复打包得到同一个
   `sha256`，校验值可以写进文档而不会隔天失效。
2. **校验以 `manifest.json` 为准**：下载完先比对 sha256 再解压，不符直接丢弃并报错，
   目录里不会留下半成品。注册表里写了 `sha256` 时以注册表为准（更严，能防 manifest 被换）。
3. **解压不越界**：`../x`、`/abs.txt`、`C:/x` 三种成员名都被跳过——注意 Windows 上
   `Path("/abs.txt").is_absolute()` 是 `False`，只判 `is_absolute()` 拦不住。

本机打包实测：10 份本地已有的数据集共 **1,299.9 MB** zip（`fish_disease` 178.2 MB、
`aquaponics_pond` 16.3 MB —— 96 MB 的 CSV 压得很狠、`fish_disease_images` 1,070.1 MB）。
`fish_disease_cleaned` 与 `fish_species_images` **本地没有，无法打包**，需要先有数据
或 Kaggle 凭证。

> **输出编码**：这些脚本都调用了 `fisheries.console.install()`，它**只放宽
> `errors`、不改编码**——改编码会让字节和终端对不上，中文反而变乱码。
> 想看正常的中文输出，让控制台保持自己的编码即可（双击入口已含 `chcp 65001`）；
> 不要自行设 `PYTHONIOENCODING=utf-8`。

2. **`Train_Augmented/`（155.3 MB，21,358 张）**——构建脚本不认这个目录名，

   否则以后想重建就得重新下载。
4. **`Sensor Based Aquaponics...`（96 MB）**——只被当作列名写法参考，
   代码不读文件内容。删掉后 `src/fisheries/tables.py` 仍然正常工作。
5. **`Fish Disease Dataset/Train` + `Valid`（22.3 MB）**——想再省可以裁，
   但 `Test/`（2 MB / 350 张）**必须留着**：`demo_agent.py` / `demo_cases.py` /
   `tests/unit/test_agent.py` 都从它取图。

按 1~4 全删：**1,395.7 MB → 约 122 MB**（只剩 `Fish Disease Dataset` 的
`Train`/`Valid`/`Test` 与几个小 CSV）。若连 5 也裁，降到约 100 MB。

6. **想把数据彻底移出工程目录**：整个 `数据集\` 挪到别的盘，然后
   `set FISHERIES_DATA_ROOT=<新位置>`。一行环境变量，代码零改动。

**另外注意：工程内现在还多了一份派生产物** `data/derived/`（22.6 MB），
是 `build_yolo_dataset.py` 从上面这些源图生成的训练/验证/测试布局
（`fish_disease_4cls` 分类版 + `fish_disease_4cls_det` 弱监督检测版 + `runs/`），
外加 `data/derived/metrics.json`。它**是可重建的构建产物**，不是原始数据；
删掉后重跑构建脚本即可复原。`models/pretrained/yolov8n-cls.pt`（5.3 MB）
是训练时的预训练权重缓存，同样可重新下载。

## 2. 图像数据集

### 2.1 类别定义（7 类，中英对照）

**中文名以数据集官方清单 `class_names` 为准**（来自平台的 `*.ndjson` 清单文件，
非本项目自行翻译）：

| 官方 ID | 官方中文名 | 英文目录名（本地） | 本项目输出类别 | 严重度权重 |
|---|---|---|---|---|
| 3 | **水霉病** | `Fungal diseases Saprolegniasis` | 水霉 | 0.70 |
| 1 | **细菌性出血病** | `Bacterial diseases - Aeromoniasis` | 出血 | 0.90 |
| 2 | **烂鳃病** | `Bacterial gill disease` | 烂鳃 | 0.85 |
| 0 | **红体病** | `Bacterial Red disease` | 出血 | — |
| 5 | **寄生虫病** | `Parasitic diseases` | 其他 | 0.75 |
| 6 | **白尾病** | `Viral diseases White tail disease` | 其他 | — |
| 4 | **健康** | `Healthy Fish` | 健康 | 0.00 |

**映射说明**：用户约定的对外接口是 4 类（烂鳃 / 出血 / 水霉 / 健康），
而底层数据集是 7 类。映射规则见 `src/fisheries/tools/fish_disease.py` 的 `RAW_CLASS_TO_LABEL`：

- **`红体病` 归入 `出血`**——红体病（赤皮病）与细菌性出血病同属细菌性体表出血性病灶，
  在养殖现场的首要处置动作一致（消毒 + 内服抗菌），合并对决策无实质损失。
- **`寄生虫病` 与 `白尾病` 归入 `其他`**——这是**刻意保留的第 5 个安全兜底值**。
  用户的接口只约定了 4 类，但强行把这两类塞进"健康"等于**把病鱼判成健康鱼**，
  在生产环境属于安全事故。因此工具输出保留 `其他`，
  同时用 `raw_class` 字段**无损保留底层 7 分类的原始判定**。
  若下游确实只需要 4 类，可把 `ALLOW_OTHER_FALLBACK` 置 `False` 强制合并到"出血"。

> ⚠ **这张表描述的是"文件夹名 → 输出标签"的映射，不是训练时的类别数。**
> 训练出的 `models/yolov8-fish.pt` 只有 **4 个原始类别**
> （`healthy` / `gill_rot` / `bacterial_hemorrhage` / `saprolegniasis`），
> 对应"健康 / 烂鳃 / 出血 / 水霉"。上表的 7 类映射仍然生效于两条路径：
> ① `mock_source="folder_hint"` 的 mock 兑底（直接读目录名猜类别）；
> ② `raw_class` 字段的原始判定回填。
> 而 `红体病` / `寄生虫病` / `白尾病` 三类**因为样本量不足以单独训练，
> 没有进训练集**，所以真实模型不会输出它们——`其他` 这个值
> 在当前真实权重下基本不会出现。

### 2.2 主训练集：`Fish Disease Dataset`

| 子集 | 每类张数 | 类别数 | 合计 |
|---|---|---|---|
| `Train` | 250 | 7 | **1,750** |
| `Valid` | 50 | 7 | **350** |
| `Test` | 50 | 7 | **350** |
| `Train_Augmented` | ~3,051 | 7 | **21,358** |
| | | **合计** | **23,808** |

- 类别分布**完全均衡**（每类张数一致），无需重采样或类别加权。
- 图片为 **224×224** 正方形 JPEG（`Train_Augmented` 是 256×256）。

> 🔴 **这张表的三个子集不能用**——2026-10-15 实测：
> 1. **`Valid` 与 `Test` 的图同时也在 `Train` 里**（每类 `Train∩Valid = 50`、
>    `Train∩Test = 50`）。**沿用这套切分必然指标虚高**，所以
>    `build_yolo_dataset.py` 丢弃上游切分、按 `sha1(文件名主干)` 自建 559/186/186。
> 2. **`Train_Augmented` 一个代码路径都不读**。`_UPSTREAM_SPLITS` 只认
>    `Train` / `Valid` / `Test` 三个目录名，`Train_Augmented` 不在其中，
>    **整目录被跳过**。而且它的文件名是 `aug_<idx>_<n>.jpeg` 格式，
>    实测 **0/3000 能匹配回 `Train` 的任意主干** → 连"增强图必须与原图同 split"
>    这条泄漏防护都无法实现（无法追溯来源）。
>    所以 §0.2 把 155.3 MB 的 `Train_Augmented` 列为**可删**。
> 3. 所谓"7 类 × 250 张 = 1,750"里有大量重复：同一张照片以
>    `.jpeg` / `.jpg` / `.png` 三种扩展名并存（字节不同、md5 不同）。
>    **按文件名主干去重后，全库只有 931 张不同照片**。

### 2.4 🔴 重要发现：三套图像数据集是**同一批照片**（已实测证实）

`Fish Disease Dataset`、`Freshwater Fish Disease Aquaculture in south asia`、
`SB-FishDisease` 的**目录结构、类别名称、文件名格式高度一致**
（均为 `<类别名> (序号).jpg`）。

原文档写的是"疑似同源，待验证"。**2026-10-15 已实测证实，而且比预想更严重**：

| 核对方式 | 结果 |
|---|---|
| `freshwater` vs `fish_disease` 逐类按 md5 | **250 / 250 完全重叠**（每类） |
| `SB-FishDisease` 的图是否已在 `fish_disease` 里 | **是，一张都不多**（healthy 158 / gill 36 / Aeromoniasis 40 / Saprolegniasis 33 全部命中） |
| 上游自带的 `Train/Valid/Test` 是否互斥 | ❌ **不互斥**：每类 `Train∩Valid = 50`、`Train∩Test = 50`、`Valid∩Test = 0` |
| 全库**真正不同**的照片数 | **931 张** |

两个关键教训：

1. **不能按 md5 去重**。同一张照片常以 `.jpeg` / `.jpg` / `.png` 三种扩展名
   各存一份，**字节不同所以 md5 不同**——按 md5 去重会漏掉这种重复，把同一张图
   分到训练集和测试集两侧。**身份识别必须用文件名主干 `(类别, stem)`。**
   （实测：按 md5 去重时报 `variants_dropped = 2199`，按主干去重才归到 931。）
2. **不能沿用上游切分**。`Valid` 和 `Test` 的图**同时也在 `Train` 里**，
   直接沿用必然指标虚高。

### 2.6 🔴 关键结论：数据集**没有检测框标注**（方案 A/B 已定）

>    **完全不衡量病灶定位**。这一点同时写在 `data/derived/metrics.json` 的

### 3.3 🔴 表头与需求字段的差异

| 需求字段 | 数据集情况 | 处置 |
|---|---|---|
| 水温 | ✅ `Temperature (C)` | 直接用 |
| pH | ✅ `PH` | 直接用 |
| 溶氧 | ✅ `Dissolved Oxygen(g/ml)` | 直接用（单位存疑，见 3.5） |
| 氨氮 | ✅ `Ammonia(g/ml)` | 直接用（单位存疑） |
| **亚硝酸盐** | ❌ **不存在** | 见下方说明 |
| 养殖密度 | ⚠ `Population` | 疑似漂移，需清洗 |
| **投料记录** | ❌ **所有文件均无此字段** | 见下方说明 |

**亚硝酸盐缺失的处理**：所有 IoTPond 文件只有 `Nitrate`（**硝酸盐**，
氮循环终产物、毒性低），**没有 `Nitrite`（亚硝酸盐**，中间产物、毒性高，
是池塘急性中毒的主因）。二者不可混用。

因此工具 `water_risk_predict` 的 `nitrite_n` 参数被设计为**可选**：
缺失时该指标整列剔除，其余指标权重自动重新归一化。
若强行设为必填，工具在真实数据上将**完全不可用**。

**投料记录缺失的处理**：投料量是水质恶化（尤其氨氮）的**首要解释变量**——
没有它，模型只能看到"氨氮升高"却无法归因。当前方案：
在 `AgentInput` 中预留投料字段，**由硬件侧补充采集**（用户负责），
在此之前投料权重（0.08）不参与计算。

### 3.5 量纲判定（**M8 第三轮已用独立判据解掉，但仍是"可被推翻的推断"**）

列名标注为 `g/ml`，但数值量级（氨氮 0.458、溶氧 4.505）不符合 `g/ml` 的物理常识
——若真是 g/ml，等于氨氮 458 g/L，是浓氨水而非养殖水体。

**最终判定分两条，不是一句话统一成 `mg/L`：**

| 列 | 判定 | 依据 |
|---|---|---|
| `Dissolved Oxygen(g/ml)` | **不换算**，就是 `mg/L` | 组内中位数 3.3～18.3；25 ℃ 饱和溶氧约 8.4 mg/L，量级吻合 |
| `Ammonia(g/ml)` | **÷1000，按 µg/L → mg/L** | 组内中位数 0.55～60。见下方独立判据 |
| `Nitrate(g/ml)` | **÷1000，同上** | 与氨氮同族标注，且 `IoTPond8` 的 `(mg/L)` 列量级恰是其余文件的 1/1000 |

**独立判据（不靠"量级看着像"）**：同一份数据里逐条记录了鱼的体长体重，而**每条塘的鱼都长得很好**——
`IoTPond7` 体重 8.0 → 998.5 g（**+12,360%**）、`IoTPond6` 3.3 → 231 g（+6,900%）。
按字面把氨氮读成 0.55～60 g/ml 相当于致死红线（1.0 mg/L）的 10⁵～10⁷ 倍：
**鱼不可能一边泡在这种水里一边增重 120 倍**，两个事实不能同真。
÷1000 之后氨氮落在 0.0006～0.06 mg/L，全在适宜带，与增重事实一致。

旁证：`IoTPond8` 是**唯一**标了 `(mg/L)` 的文件（`Ammonia (mg/L)` 中位数 0.00111、最大 0.9966），
数值恰是其余文件 ÷1000 后的同一量级。

**落地位置**：`evaluation/ponds.py` 的 `UNIT_DIVISORS`（可改常量）。
**影响面**：改掉它，M8 报告里第一组的氨氮分档会整体偏移——所以依据写在报告 2.2 节供人推翻。
**仍未做**：向设备厂商核对实际量纲。这件事没做，上面就只能是推断。

### 3.6 采样频率

实测**间隔中位数 20 秒**（不是「约 1 分钟/条」；`IoTPond8` 是例外，中位数 **1440 分钟**，
即每天一条——它同时也是唯一用 ISO 带偏移时间戳的文件）。

**M8 的实际处置是聚合到 10 分钟**（`evaluation/ponds.py:AGGREGATE_MINUTES = 10`），
数据量从 111 万行压到 4.9 万个聚合点（约 23 倍），再按 3 小时开窗。
选 10 分钟而不是 1 小时，是因为**引擎的「3 小时内骤降 2.0 mg/L」判据需要足够细的粒度**
才能看出下降速率；1 小时的桶会把骤降平均掉。

### 3.7 ⚠ 缺少发病标签

所有 IoTPond 文件**都没有"是否发病"标签**，
只有水质读数，没有"这批鱼后来生病了吗"的结果变量。

**影响**：无法直接做有监督的"水质 → 发病"预测。
**当前对策**：

1. 风险等级由**行业标准阈值规则**判定（本项目 `water_risk.py` 的做法），
   而非数据驱动的模型；
2. 后续接入 LSTM 时，采用**自监督/重构式**训练目标
   （用历史窗口预测未来窗口的指标值），而非分类目标；
3. 需用户通过硬件侧补充**人工巡塘记录 / 死鱼记录 / 用药记录**，才能补上标签。

### 3.8 采用范围

| 文件 | 决定 | 理由 |
|---|---|---|
| `IoTPond1/2/3/4/6/7/8/9` | ✅ **主用** | 数据量充足、时间跨度连续；M8 的 3,183 个评测窗口主要来自这 8 口塘 |
| `IoTPond10/11/12` | ⚠ **读但样本极少** | 只有 620/3,165/3,590 行、时间戳可解析率 50%/20%/0.7%，清洗后分别只剩 28/53/2 个聚合点。M8 起初想弃用，后来改为**照读但单独看**——把它们从报告里删掉等于隐瞒「这份数据有 3 个文件基本不可用」，留着反而让逐塘表把这件事说清楚（`IoTpond12` 的 2 个样本在逐塘 P/R/F1 里会明显劣化） |

## 4. 已停用与参考数据

### 4.1 `Dissolved oxygen prediction in river water` ⛔ 已停用

| 文件 | 数据行数 |
|---|---|
| `train.csv` | 147 |
| `test.csv` | 63 |

宽表结构：`O2_1..O2_7`、`NH4_1..NH4_7`、`NO2_1..NO2_7`、`NO3_1..NO3_7`、`BOD5_1..BOD5_7` + `target`。

即：**用前 7 个时刻的观测预测下一个时刻的溶氧**，本质是一个时序回归任务。

- 数据来自**河流断面**，不是池塘，水质基线与昼夜规律不同；
- 它**唯一的好处是带 `NO2`（亚硝酸盐）字段**——但那条宽表**没有绝对时间单位**，
  "一步"是多长只能假定。

**停用记录**：M8 第二轮用它做过溶氧外推评测（144 条序列，引擎 MAE 2.719 vs 持久性基线 1.638，
**劣于基线 66.0%**）。结论本身成立且可量化，但**尺子量错了对象**——引擎的
"3 小时内骤降 2.0 mg/L"这类判据在河川宽表上无从触发。
M8 第三轮改用 `aquaponics_pond` 的溶氧序列重跑同一套协议：最初的全量斜率外推仍是
**劣于基线 14.5%**，改成混合基线（锚点平滑 + 5% 斜率修正）后**优于基线 9.8%**
（真值独立，是报告里唯一可以对外引用的性能数字）。
数据仍留在磁盘上（0.5 MB 级），`datasets.py` 里保留注册项并标注「已停用」。

### 4.2 `china_water_pollution_data.csv` ⛔ 已停用

3,001 行 × 49 字段，2023 年，**格式干净**。

含字段：水温、pH、溶氧（mg/L）、氨氮、亚硝酸盐、多种重金属、`WQI` 水质指数、
`Pollution_Level` 分级标签。

**停用记录**：M8 第一轮用它做过规则外部验证，测出准确率 31.9%、Cohen's κ -0.011、
Spearman ρ -0.028——三个数字接近随机。诊断结论**不在引擎**：把标签严重度与数据集里
**每一个**数值列算 Spearman ρ，结果是 **|ρ| 全部 < 0.03**，其中包含数据集**自带的**
`Water_Quality_Index`（ρ -0.029），且每个五级标签下的测量值分布完全一致。
**真值不由测量值决定，标签不可用。**
（该数据集面向**地表水环境质量标准** GB 3838，与渔业水质标准 GB 11607 及池塘养殖阈值也不一致。）
数据仍留在磁盘上，`datasets.py` 里保留注册项并标注「已停用」。
