## 1. 项目定位与目标

### 1.1 一句话定位

面向淡水池塘养殖户的**工具调用型 AI Agent**：接收水质时序数据与鱼体图片，自动完成「数据清洗 → 水质风险预测 → 病害识别 → 多源融合 → 风险等级与可落地调控建议」全链路，把模型输出的冷数值翻译成养殖户看得懂、能执行的操作方案。

### 1.2 与"纯对话机器人"的区别（答辩必须讲清的差异点）

| 维度 | 纯对话 LLM | 本项目 Agent |
|---|---|---|
| 输入 | 文本 | 传感器时序 + 图像 + 文本 |
| 决策依据 | 模型参数里的先验知识 | 实时水质数值 + 图像证据 + 行业标准阈值 |
| 输出可验证性 | 无法追溯 | 每个结论可回溯到具体指标值、模型置信度、知识库条目 |
| 工具能力 | 无 | 时序预测、病害识别、RAG 检索、规则引擎 |

### 1.3 大赛评分对齐

| 评分维度 | 本项目对应产出 |
|---|---|
| 完整工程链路 | Label Studio 标注 → pandas 清洗 → 标准化 → 模型训练 → API 封装 → Agent 调度 |
| 技术创新性 | 多源融合决策（时序 + 图像证据协同放大）、双模态输入、RAG 引证 |
| 场景价值 | 缺氧翻塘、鱼病延误诊断，直接对应养殖户经济损失 |
| 可落地性 | Streamlit 演示原型 + FastAPI 后端 + 阈值规则全部来自行业标准 |

## 2. 需求与场景

### 2.1 目标用户

淡水池塘养殖户（中小规模、缺专业技术员），核心诉求是"**今晚会不会翻塘**"和"**这条鱼得的什么病、怎么治**"。

### 2.2 三类输入 → 三条处理链路

| 输入类型 | 触发链路 | 输出现象 |
|---|---|---|
| 水质时序数据（CSV / 传感器流） | 清洗 → 特征 → 时序风险预测 → 阈值判定 | 未来变化趋势、风险等级、调水建议 |
| 鱼体图片 | 预处理 → 病害识别 → 类别 + 置信度 | 病害名称、置信度、用药/消毒方案 |
| 自然语言提问 | RAG 知识库检索 + 历史数据 | 带引用的专业回答 |

**融合场景（本项目的技术亮点）**：同时输入水质与图片时，不是两个结论简单拼接，而是做**证据协同判定** —— 例如「氨氮超标 + 检出细菌性烂鳃病」的组合风险高于任一单项，需触发升级告警。

### 2.3 关键约束

1. 代码优先 Python，工具调用使用**函数调用（function calling）**；
2. 所有水产专业规则遵循淡水池塘养殖行业标准；
3. 分模块开发，一次只完成一个模块；
4. 每个模块交付：代码 + 注释 + 输入输出样例 + 测试用例；
5. 接到传感器数据或病害识别结果时，需模拟 Agent 决策推理过程；
6. 代码结构规范，附带 README、数据集说明。

## 3. 总体架构

### 3.1 五层架构

```
┌─────────────────────────────────────────────────────────────┐
│ L5 交互层    Streamlit 网页（主演示） / FastAPI / 预留 QQ 机器人 │
├─────────────────────────────────────────────────────────────┤
│ L4 智能体层  Agent 调度器 + 工具注册表 + 提示词体系 + 会话记忆   │
│              ├─ 意图识别与任务规划（LLM function calling）      │
│              └─ 多源融合决策器（规则引擎 + 证据加权）            │
├─────────────────────────────────────────────────────────────┤
│ L3 工具层    ①水质预测工具 ②病害识别工具 ③RAG检索工具          │
│              ④规则判定工具 ⑤建议生成工具 ⑥历史数据查询工具     │
├─────────────────────────────────────────────────────────────┤
│ L2 模型层    LSTM/TCN 水质时序模型  |  YOLO 鱼病识别模型        │
│              (负责人训练交付)        |  (负责人训练交付)         │
├─────────────────────────────────────────────────────────────┤
│ L1 数据层    IoTPond 时序数据 + Fish Disease 图像数据           │
│              数据清洗管线 → 特征工程 → 标准化器（持久化）        │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 端到端数据流

```
传感器/CSV ──► [清洗] ──► [特征] ──► [时序模型] ──► 风险分 S_w ┐
                                                              ├─► [融合器] ─► 风险等级
鱼体图片 ────► [预处理] ─► [YOLO]  ──► 病害+置信度 ──► S_d    ┘        │
                                                                        ▼
养殖户提问 ──► [RAG 检索] ──► 知识片段 ────────────────────────► [LLM 生成器]
                                                                        │
                                                                        ▼
                                                        风险等级 + 告警 + 调控建议（可引证）
```

### 3.3 设计原则

1. **模型可替换**：L1/L2 与 L3 之间通过数据契约解耦，负责人后续换更强的模型不影响 Agent 层。
2. **降级可用**：任一模型不可用时（模型未训练完 / 推理失败），走规则基线分支，Agent 不崩、给友好提示。
3. **结论可追溯**：每个输出结论必须携带 `evidence` 字段，指向具体指标值、模型置信度、知识库条目 ID。
4. **阈值可配置**：所有行业阈值走 YAML 配置，不硬编码，便于按养殖品种校准。

**已发现的真实数据质量问题（清洗模块的验收标准）**

| # | 问题 | 实例 | 影响 |
|---|---|---|---|
| Q1 | 列名不一致 | `Temperature (C)` vs `TEMPERATURE` vs `Lenght`（拼写错误） | 合并多文件时错列 |
| Q2 | 时间格式至少 4 种 | `2021-06-19 00:00:05 CET` / `... UTC` / `2021-06-18T13:06:49+01:00` / `5/12/2021` | 无法直接解析 |
| Q3 | `entry_id` 列混入日期 | IoTPond7 首行 `entry_id` 值为 `18-06-` | 需按位置重新映射 |
| Q4 | 末行列错位 / 空值 | `29/1/2022,,,,,,,,75,48.11,801` | 末行解析出脏记录 |
| Q5 | 量纲跨文件不一致 | Ammonia：IoTPond1 为 `0.458`，IoTPond11 为 `12151` | 已判定：溶氧不换算、氨氮与硝酸盐 ÷1000（见下方引用块） |
| Q6 | 量程已坏 | `Turbidity(NTU)` 大量读数恰好等于 `100`（封顶），另有负数 −97/−57/−56/−51/−10 | 不分档、不参与标签 |
| Q7 | 疑似漂移/误标 | `Population` 逐行变化（189 → 194），养殖密度应为稳定值 | 特征不可信，需按日聚合或取众数 |
| Q8 | 时间跨度异常 | `IoTPond10` 结束早于开始 84.9 分钟、`IoTPond12` 早 652 毫秒 | 排序混乱，需校验 |
| Q9 | 缺失值 | `Dissolved oxygen...\train.csv` 大量空列 | 需前向填充或掩码 |

> **物理量纲校验（重要工程判断）**
> 列名标注单位 `Dissolved Oxygen(g/ml)` 与 `Ammonia(g/ml)` 在物理上不合理（g/ml 是密度量级，会得到 4.5 g/mL 的溶氧）。实际数值量级（DO≈4.5、Ammonia≈0.46）**更接近 mg/L**。
>
> **M8 落地时的结论（比这里更细，且有独立判据）**：溶氧**不换算**（中位数 3.3～18.3，就是 mg/L）；
> 氨氮与硝酸盐按 **µg/L ÷1000** 处理。判据不是"量级看着像"，而是同一份数据里的**鱼体长体重**——
> 每条塘的鱼都长得很好（IoTPond7 体重 8.0 → 998.5 g，+12,360%），按字面 g/ml 读却是致死红线的百万倍，
> 两者不能同真；而唯一标 `(mg/L)` 的 IoTPond8 量级恰好是其余文件的 1/1000，是最强旁证。
> 系数落在 `evaluation/ponds.py:UNIT_DIVISORS`，可改；依据与影响面写在 `docs/M8_评测报告.md` 2.2 节。
> 向采集方确认设备真实量纲这件事**仍然没做**，所以这条推断仍标着"可被推翻"。

## 5. 数据契约（Schema 设计）

> 全部使用 Pydantic v2 `BaseModel` 定义。这是**所有模块之间的唯一接口约定**，M0 阶段先落地，后续模块只依赖它。

### 5.1 核心契约总览

```
SensorReading      原始传感器单条读数（输入端）
SensorWindow       清洗后的定长窗口（清洗模块输出 → 预测模块输入）
ImageSample        图像样本（输入端）
VisionResult       病害识别输出（识别工具 → 融合器）
WaterRiskResult    水质风险输出（预测工具 → 融合器）
RiskLevel          风险等级枚举（安全 / 预警 / 高危）
FusedAssessment    融合评估结果（融合器 → Agent）
Evidence           证据条目（可追溯性载体）
Advisory           单条调控建议
DecisionReport     最终决策报告（Agent → API → 前端）
ToolCall / ToolResult  工具调用记录（推理轨迹留痕）
```

### 5.2 字段定义

**`RiskLevel`（枚举）**

| 值 | 含义 | 触发条件（概述） |
|---|---|---|
| `SAFE` | 安全 | 融合风险分 < 40 |
| `WARNING` | 预警 | 40 ≤ 风险分 < 70 |
| `CRITICAL` | 高危 | 风险分 ≥ 70，或命中任一红线规则 |

**`SensorReading`**

| 字段 | 类型 | 单位 | 必填 | 约束 |
|---|---|---|---|---|
| `pond_id` | str | — | ✅ | 池塘编号 |
| `timestamp` | datetime | — | ✅ | 统一为带时区 UTC |
| `water_temp` | float | ℃ | ✅ | −5 ~ 45 |
| `ph` | float | — | ✅ | 0 ~ 14 |
| `dissolved_oxygen` | float | mg/L | ✅ | 0 ~ 25 |
| `ammonia_n` | float | mg/L | ✅ | 0 ~ 50 |
| `nitrite_n` | float | mg/L | ⭕ | 0 ~ 50 |
| `nitrate_n` | float | mg/L | ⭕ | 0 ~ 500 |

| `limiting_factor` | str | 主控因子（如 `dissolved_oxygen`） |
| `rule_hits` | list[str] | 命中的规则 ID（如 `DO_MIN_CRITICAL`） |
| `feature_contributions` | dict[str, float] | 特征贡献度（可解释性） |
| `degraded_mode` | bool | True 表示走了规则基线而非模型 |

**`Evidence`**：`source`（`sensor` / `vision` / `knowledge` / `rule`）、`ref`（引用 ID）、`summary`（人话描述）、`value`（原始值）、`weight`（0~1 权重）

**`Advisory`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `priority` | int | 1 = 立即执行 |
| `category` | str | `增氧` / `调水` / `投喂` / `用药` / `监测` / `捕捞` / `消毒` |
| `action` | str | 具体操作 |
| `reason` | str | 依据（关联指标/病害/知识条目） |
| `citation_ids` | list[str] | 知识库条目 ID 列表 |
| `deadline_hint` | str | 如"今日 22:00 前" |
| `risk_if_ignored` | str | 不执行的后果 |

**`DecisionReport`**（最终输出）

| 字段 | 类型 | 说明 |
|---|---|---|
| `report_id` / `pond_id` / `generated_at` | str/datetime | 元信息 |
| `risk_level` / `risk_score` | RiskLevel / float | 总等级 |
| `headline` | str | 一句话告警（≤ 40 字） |
| `summary` | str | 自然语言综合分析 |
| `evidence` | list[Evidence] | 全部证据 |
| `water_risk` | WaterRiskResult \| None | 水质分支结果 |
| `vision_result` | VisionResult \| None | 图像分支结果 |
| `advisories` | list[Advisory] | 可落地建议，按 priority 排序 |
| `escalation_reason` | str \| None | 融合升级原因（协同放大触发时填写） |
| `tool_trace` | list[ToolCall] | 工具调用轨迹（可解释性 / 答辩展示） |
| `disclaimer` | str | 用药需遵医嘱、按说明书剂量的免责说明 |

> ⚠ **实施同步（2026-10-14）**：上表是**设计期契约**，实际实现已收敛为更小的集合。
> 权威定义在 `src/fisheries/agent/orchestrator.py` 与 `src/fisheries/agent/fusion.py`，
> 不再有 `DecisionReport` 这个类名，实际返回 **`AgentResult`**：
>
> - `report: dict` —— 建议角色的四块结构化输出（`risk_level` / `headline` / `alerts` /
>   `water_actions` / `disease_actions` / `observation_window` / `confidence_note`），见 §8.3；
> - `advisories: list[Advisory]` —— 由 `report` 的两条动作清单**合并排序**得到，供只想要
>   平铺列表的调用方使用（`Advisory` 实际只有 `priority` / `target` / `action` / `timing`
>   四个字段，**没有** `category` / `citation_ids` / `deadline_hint` / `risk_if_ignored`）；
> - 出处不放在每条建议里，而是整份报告的 `references: list[str]`（形如
>   `《文档标题》> 小节名（未核对标准原文）`）+ `knowledge_block: str`（实际注入提示词的 RAG 原文）；
> - 水/图/融合三个分支保留**工具层原始 dict**（`water` / `vision` / `fusion`），
>   不在 Agent 层重建等价模型——那会在工具改字段时静默漂移；
> - `risk_score` → `fused_score`；`escalation_reason` → `reason`（融合层规则拼装）；
> - `disclaimer` 放在 `GET /api/v1/config/thresholds` 的响应里，而不是每份报告里。

## 7. 核心算法与规则设计

### 7.1 水质指标阈值表（工程默认值 v0.1）

> ⚠️ **待核对项**：下表为行业常规经验的工程默认值，用于先跑通链路。**正式版必须与现行标准原文逐条核对后再定稿**，并标注所引标准号。建议核对来源：《渔业水质标准》GB 11607、无公害食品淡水养殖用水水质 NY 5051 系列、SC/T 9101 淡水池塘养殖水排放要求，以及所养殖品种（鲤科 / 罗非鱼 / 虾蟹）的专项要求。
> ⚠️ **品种差异**：温水性鱼类（鲤、草鱼）与罗非鱼、虾蟹类的适宜温区与氨氮耐受度差别显著，阈值配置需支持按品种切换。

| 指标 | 适宜 | 警戒 | 危险 | 判定要点 |
|---|---|---|---|---|
| 水温 | 20 – 30 ℃ | 15 – 20 或 30 – 33 ℃ | < 15 或 > 33 ℃ | 日变幅 > 3 ℃ 触发应激告警 |
| pH | 6.5 – 8.5 | 6.0 – 6.5 或 8.5 – 9.0 | < 6.0 或 > 9.0 | 日波动 > 1.0 提示藻相失衡 |
| 溶解氧 DO | ≥ 5 mg/L | 3 – 5 mg/L | < 3 mg/L（< 1.5 泛塘级） | **按日最低值判定**，最低值出现在凌晨 4–6 时 |
| 氨氮 NH₃-N | ≤ 0.2 mg/L | 0.2 – 0.5 mg/L | > 0.5 mg/L | 分子氨毒性随 pH、水温升高而放大，需联合判定 |
| 亚硝酸盐 NO₂⁻-N | ≤ 0.1 mg/L | 0.1 – 0.3 mg/L | > 0.3 mg/L | > 0.3 易发褐血病 |
| 硝酸盐 NO₃⁻-N | ≤ 50 mg/L | 50 – 100 mg/L | > 100 mg/L | 慢性毒性，偏低优先级 |
| 透明度 | 25 – 40 cm | < 25（过肥）或 > 40（过瘦） | — | 需人工录入或图像估算 |
| 投饵率 | 体重的 2 – 5 % | > 5 % | — | 过量投料是氨氮主要来源，与投料记录联动 |

**分子氨（NH₃）联合判定规则**：非离子氨占比随 pH 与水温上升而升高。当 `pH > 8.5` 且 `water_temp > 28 ℃` 时，即使 `ammonia_n` 处于"警戒"区间，也应**升级为"危险"**判定。

### 7.2 风险分计算（规则基线）

```
risk_score = clip( Σ_i ( w_i × severity_i ) × persistence_multiplier , 0, 100 )

w_i          : 指标权重（DO 0.35 / 氨氮 0.20 / 亚硝酸盐 0.15 / pH 0.12 / 水温 0.10 / 投料 0.08）
severity_i   : 0（适宜）| 0.5（警戒）| 1.0（危险）
persistence  : 1.0 + 0.1 × (连续超阈点数 − 1)，上限 1.5
```

**红线规则（命中即直接 CRITICAL，无视加权分）**

| 规则 ID | 条件 |
|---|---|
| `DO_REDLINE` | 预测未来 12h 内 DO < 1.5 mg/L |
| `NH3_REDLINE` | 氨氮 > 1.0 mg/L |
| `NO2_REDLINE` | 亚硝酸盐 > 0.5 mg/L |
| `PH_REDLINE` | pH < 5.5 或 > 9.5 |
| `DO_CRASH_TREND` | DO 3 小时内下降幅度 > 2 mg/L |

> 训练脚本 `scripts/train_yolo_fish.py`，权重 `models/yolov8-fish.pt`（YOLOv8n-cls，
> 1,443,412 参数 / 3.4 GFLOPs），留出集 186 张：**Top-1 93.01% / 宏 F1 93.02% /

>
> 1. **数据比名义上少得多**。7 个类别文件夹看着不小，但按文件名主干去重后

>    等价于按置信度排序的分类 AP 均值。评测报告与 `metrics.json`
>    都写了 caveat，**不要拿它当检测指标引用**。
> 3. **Grad-CAM 那个折中推荐没有实现**。当前可解释性来自融合层的证据链
>    （`severity_weight × confidence` + `VISION_DISEASE` / `VISION_HEALTHY` 证据项），
>    不是热力图。要真做定位，前置条件仍是补标注框。

**严重度权重映射**

| 类别 | severity_weight 基准 |
|---|---|
| 病毒性白尾病 | 0.95（无特效药，需隔离） |
| 细菌性败血症 | 0.90 |
| 细菌性烂鳃病 | 0.85 |
| 水霉病 | 0.70（早期可控） |
| 细菌性赤皮病 | 0.65 |
| 寄生虫病 | 0.55 |
| 健康 | 0.0 |

> 实际落地的是**五档中文标签 + 连续相乘**：
>
> | 实际标签 | `severity_weight` | 分组 | 来源 |
> |---|---|---|---|
> | 出血 | 0.90 | 细菌性 | 训练类别 `bacterial_hemorrhage` |
> | 烂鳃 | 0.85 | 细菌性 | 训练类别 `gill_rot` |
> | 其他 | 0.75 | 其他 | 未映射到上面三类的兜底（mock 的 `hash` / `folder_hint` 会出现） |
> | 水霉 | 0.70 | 真菌性 | 训练类别 `saprolegniasis` |
> | 健康 | 0.00 | 健康 | 训练类别 `healthy` |

> 见 `src/fisheries/tools/fish_disease.py` 的 `LABEL_META`。
>
> **两处刻意的偏离及理由**：
> 1. **不做置信度分档**，改用 `severity_weight × confidence` 连续相乘
>    （`agent/fusion.py` 的 `_vision_score`）。分档会在 0.849 与 0.851 之间
>    制造 20% 的跳变，而"把握 0.3 的烂鳃"和"把握 0.95 的烂鳃"本来就该有
>    连续可分的高低——**分档是设计期的简化，实现时没有理由再保留**。
> 2. **七类压成四类训练**：`Fish Disease Dataset` 名义上有 7 个文件夹，但去重后
>    真正不同的照片只有 931 张，其中"细菌性败血症 / 赤皮病 / 寄生虫病 / 白尾病"
>    四类样本量不足以单独训练。训练目标收敛为需求里点名的四类
>    （健康鱼 / 烂鳃 / 细菌性出血 / 水霉），其余归"其他"。
>    详见 [模型训练说明.md](模型训练说明.md)。
>
> 因此设计表里的「病毒性白尾病 0.95 / 细菌性赤皮病 0.65 / 寄生虫病 0.55」
> **当前不会出现**——除非以后补足这些类别的样本再扩类。

**与负责人对接的输出契约**：模型交付时需一并提供 —— 权重文件路径、**类别顺序文件**（`classes.json`，顺序必须与训练时一致）、推理输入尺寸与归一化参数、模型版本号。缺少类别顺序是集成时最常见的错误来源。

### 7.4 多源融合策略

> ⚠ **实施同步（2026-10-14）**：本节公式为设计期写法，实际实现增加了**等级下限**
> （level floors）机制，见本节末尾「实施同步」小节与 README §6.1。
> 仅靠加权平均会把「水质高危 + 照片上鱼看着健康」压成预警。

```
weighted_score = w_water × S_water + w_vision × (S_vision × 100) + synergy_bonus
                 （仅单模态时，另一项权重置 0 并归一化）

w_water = 0.6，w_vision = 0.4（默认，可配置）

synergy_bonus 触发条件（协同放大，本项目核心创新点）：
  ① 水质 WAARNING/CRITICAL ∧ 细菌性病害检出       → +12
  ② 氨氮或亚硝酸盐 超警戒 ∧ 检出任何病害            → +8
  ③ DO 预测低谷 ∧ 检出烂鳃病                        → +15（鳃损伤 → 耐低氧能力下降）
  ④ 水温处于水霉适宜区间(15–25℃) ∧ 检出水霉病       → +10
  ⑤ 任一红线规则命中                                → 直接 CRITICAL
```

**等级判定**：`fused_score < 40` → SAFE；`40 ≤ fused_score < 70` → WARNING；`≥ 70` 或命中红线/升级规则 → CRITICAL。

#### 7.4.1 实施同步：等级下限（level floors）

**加权平均隐含的假设在本项目不成立。** 加权平均假设两个模态在测**同一个潜在量**，
因此可以互相抵消。但 `S_water` 衡量的是**环境危害**（溶氧 1.9 mg/L，当晚就可能泛塘），
`S_vision` 衡量的是**已见病征**。「水质高危 + 照片上鱼看着还行」不等于风险减半，
只是**症状还没出现**。实测反例（`scripts/demo_cases.py` 第 3 组）：

```
输入：溶氧 1.9 / 氨氮 0.72 / 亚硝酸盐 0.35（三项 severity = 1.0）
      水质工具独立判定 → 高危 / 100.0 分
      + 一张健康鱼照片（0.95）→ S_vision = 0
加权：0.6×1.0×100 + 0.4×0×100 = 60.0 → 落在 40–70 区间 → 被判【预警】
```

等于是「照片上鱼看着还行」把水质高危稀释掉了。因此实际实现的定级是
**取分数档位与若干下限的最高档**：

| 下限 ID | 触发条件 | 档位 |
|---|---|---|
| `REDLINE` | 水质工具命中红线 | 高危 |
| `SEVERE_DISEASE` | 高致病性病害且置信度 ≥ 0.70 | 高危 |
| `WATER_LEVEL:高危` / `WATER_LEVEL:预警` | 水质工具**自身**的判决等级 | 高危 / 预警 |
| `DISEASE_DETECTED` | 非健康 ∧ severity_weight ≥ 0.70 ∧ confidence ≥ 0.40 | 预警 |

三条实现决策及其理由：

1. **水质下限只信任工具自己的 `risk_level`，不从 `risk_score` 反推。**
   否则会与"按分数分档"的既有语义打架（例：`risk_level=正常` 但 `risk_score=100`
   的人造输入，两种解释会给出相反结论）。
2. **病害下限的置信度门槛取 0.40，而不是工具自身的低置信线 0.60**——两者语义不同。
   低于 0.60 表示"需要人工复核"，但"需要复核" ≠ "可以按正常处理"：
   确诊流程仍要启动，只是同时附一条复核提示。0.40 以下才是纯噪声。
3. **下限一旦生效，`fused_score` 被抬到对应档线**（预警 40 / 高危 70），
   同时把纯公式值记进 `weighted_score`、抬升值记进 `score_floor`、
   触发原因记进 `level_floors`，并追加一条 `LEVEL_FLOOR` 告警。
   只加一个 `floor` 字段而不动分数，会让报告出现「高危 / 32.3 分」；
   接口消费方常按分数排序或筛阈值，这种自相矛盾会造成**漏报**。
   保留 `weighted_score` 是为了不丢信息——审计时仍能看到原始公式值。

下限只可能**抬高**等级，不会压低；它也不改变任何模态分数，
只是拒绝让一个模态的高风险被另一个模态的"正常"稀释。

**降级策略**：仅有水质数据 → 按水质单项判定；仅有图像 → 按病害严重度判定；两者皆无 → 返回参数缺失提示。

| 向量库 | Chroma 或 FAISS | Chroma（cosine 空间，`knowledge/chroma/`），带**构建清单 + 一致性守卫**：语料改了没重建会检出而不是静默用旧库 |
| 向量模型 | 未指定 | `BAAI/bge-small-zh-v1.5`（512 维，ONNX + fastembed）。模型缓存 90.8 MB **已内置到 `models/fastembed/`**，现场断网可跑 |

**定向检索策略**（`plan_queries`，固定产出 1–4 条，顺序即优先级）：

| # | 用途 | 触发条件 |
|---|---|---|
| ① | 应急处置 | **仅在高危或命中红线时检索**。预案全是「立即/紧急」祈使句，正常状态下混入会让模型把日常巡检写成紧急告警 |
| ② | 水质调控 | 永远检索，带上主控风险因子 |
| ③ | 病害处置 | 检出病害时检索，用 `disease` 硬过滤病种 |
| ④ | 投料管理 | 有病害时**也要**检索——「停料几天、怎么恢复」只有投料规范里写了 |

> 在 12 选 8 时被整块丢掉，而病害处置第一步几乎都是「停料」，恰在最需要时消失。

> **实际 schema 以代码为准**：`src/fisheries/tools/definitions.py` 的 `TOOL_SCHEMAS`，
> 用 `fisheries.tools.get_tool_schemas()` 导出为 OpenAI function calling 原生格式。
>
> **只有前两个工具暴露给大模型**。`fuse_and_decide` 与 `make_advisory`
> 在原设计中列为工具，但实现时改为**由调度层直接调用**——理由见
> [README.md](../README.md) 第 6.1 节：融合决策必须确定性、可复现、可审计，
> 交给 LLM 决定"要不要融合""怎么融合"会引入不可控的失败模式。

> 实际落盘的 function calling schema 在 `src/fisheries/tools/definitions.py`，
> 可用 `fisheries.tools.get_tool_schemas()` 直接导出给大模型。
> 已实现的两个工具位于 `src/fisheries/tools/water_risk.py` 与 `fish_disease.py`。

**Agent 执行循环**

```
1. 解析输入 → 判定需要哪些工具（LLM 决策，非硬编码 if-else）
2. 循环调用工具（最多 max_tool_rounds=5 轮），每轮记录 ToolCall
3. 融合器产出 FusedAssessment（结构化，不含自然语言）
4. RAG 定向检索（依据融合结论决定查哪几类资料；知识库不可用时降级为「无依据建议」）
5. LLM 基于【结构化评估 + 知识片段】生成 DecisionReport
6. 校验：所有数值必须来自工具输出，禁止 LLM 自行编造指标值
```

> **反幻觉约束（写进系统提示词）**：LLM 只能引用工具返回的数值；缺失数据必须写"数据缺失"，不得推测填充；用药建议必须限定在知识库检索到的范围内。

## 8. 提示词体系设计

> ⚠ **本节已按实际实现重写（2026-10-14）**。原计划把提示词拆成 `prompts/` 下 7 个 `.md` 文件；
> 实际实现改为**集中在 `src/fisheries/agent/prompts.py` 的 Python 常量**。理由见下。

### 8.1 原计划 vs 实际实现

| 维度 | 原计划 | 实际实现 | 偏离理由 |
|---|---|---|---|
| 存放形式 | `prompts/*.md` 7 个文件 | `agent/prompts.py` 4 个常量 + 3 个渲染函数 | 提示词要引用阈值表、告警结构、知识块**动态拼装**；裸 `.md` 文件做不到，只能变成模板变量，反而多一层解析 |
| 文件数 | 7（意图路由 / 水质 / 图像 / 融合 / 建议 / 兜底） | 2 个系统提示词（调度 + 建议） | 意图判定与工具选择合并进**调度角色**——它本来就要输出 `tool_calls`，再单独做一次意图分类是多余的一次 LLM 调用；水质结论 / 融合理由由**规则引擎**生成，不经过 LLM（见决策一） |
| 输出校验 | "强制 JSON Schema 校验" | Pydantic 模型 + `_coerce_actions()` 逐条丢弃非法条目 | 单条建议字段缺失不应让整份报告失败——宁可少一条建议 |
| 版本管理 | 随代码纳入 git | 同左 | 无偏离 |

### 8.2 实际提示词清单

| 常量 / 函数 | 位置 | 用途 | 要点 |
|---|---|---|---|
| `DOMAIN_CONSTRAINTS` | `prompts.py` | 共享领域约束 | 淡水池塘背景、全部阈值区间、两条领域知识（**分子氨毒性受 pH/水温放大**、**溶氧昼夜节律：日出前后 2–6 时泛塘高发**） |
| `SCHEDULER_SYSTEM_PROMPT` | `prompts.py` | 调度角色 | 四条铁律（不得编造数值；有数据必须调工具；不做定级不写建议；只用中文）+ 工具选择判断 + 参数要求（**必须对象数组，不要数组套数组**） |
| `ADVISOR_SYSTEM_PROMPT` | `prompts.py` | 建议角色 | 面向养殖户的四块 JSON 输出契约 + 正反例对照 + 四条铁律（见 8.3） |
| `ADVISOR_USER_TEMPLATE` | `prompts.py` | 建议角色用户消息模板 | 注入融合决策 / 水质块 / 图像块 / 证据链 / 告警列表 / **知识库参考资料** |
| `build_scheduler_context(ctx)` | `prompts.py` | 调度角色上下文 | 在系统提示词后用 `##CTX##` 标记注入 JSON 上下文，供 MockLLM 与真实模型共用同一解析路径 |
| `_fmt_water_block` / `_fmt_vision_block` | `prompts.py` | 工具结果 → 可读文本 | 结构化数据转文本而非 `json.dumps`——模型对"溶氧 2.6 mg/L（趋势：下降）"比对嵌套 JSON 更不容易读错 |
| `build_advisor_user_message(fusion, water, vision, knowledge_block)` | `prompts.py` | 渲染建议角色用户消息 | `knowledge_block` 为空时**必须**给显式占位文案（"本次未检索到知识库条目……不要编造出处"）——空字符串会让模型看到"知识库参考资料："后什么都没有，它更可能去编资料 |

### 8.3 建议角色输出契约（面向养殖户，四块 JSON）

```json
{
  "risk_level": "高危",
  "headline": "溶氧快见底了，先开增氧机。",
  "alerts": [{"level": "critical", "title": "水质红线告警", "detail": "…"}],
  "water_actions":   [{"priority": 1, "target": "溶氧", "action": "…", "timing": "…"}],
  "disease_actions": [{"priority": 1, "target": "烂鳃", "action": "…", "timing": "…"}],
  "observation_window": "6 小时后复测溶氧…",
  "confidence_note": "依据：水质 24 点 + 图片检出烂鳃（把握 0.86）。不确定：结论含 12.0 小时外推。复核：建议尽快补测一次水质。"
}
```

> `confidence_note` 不是自由文本：它的**内容由规则算**，模型只照固定三句式措辞，
> 详见 §8.7。

**水质块与病害块必须分开**：两块的读者动作完全不同——水质块是"今晚就要动手"，
病害块往往要隔离、要用药、有停药期；混在一个数组里前端无法分别渲染，
模型也容易把"开增氧机"和"捞病鱼"写成同一条。

**语言规则（附正反例对照写进提示词）**：

| 规则 | ✗ 反例 | ✓ 正例 |
|---|---|---|
| 说人话 | 加强水质管理，密切关注溶氧变化 | 把增氧机开到最大，天亮前不要停 |
| 给数字 | 注意氨氮浓度 | 氨氮 0.62，超警戒线 3 倍 |
| 给时限 | 适时增氧 | 现在就开，至少守到早上 8 点 |
| 给顺序 | 采取综合措施 | ①开增氧机 ②停料 ③换 1/3 水 |

**知识库使用规则**（RAG 接入后追加的第四条，与决策五配套）：
① 资料只决定"措施怎么写"，用来把动作写具体（用多少量、什么时候做、按什么顺序）；
② 资料里的**数值阈值**与"水质风险"块冲突时**一律以实测为准**；
③ 资料标注「⚠ 未与标准原文核对」的，引用其数值时必须带一句"该数值需与现行标准原文核对"（已核验的资料改带「依据 GB 11607-1989；核验日期 2026-10-15」，本项目 9 篇语料现已全部核验）；
④ 资料里没有的措施不要写，不要凭常识补充资料之外的用药方案。

### 8.4 护栏：模型写错等级 → 整份作废

`risk_level` 与 `alerts` 一律由融合层强制回填。但**只回填等级会得到一个自相矛盾的报告**——
顶部写「高危」、正文写「水质正常，一切良好」。这种报告比没有报告更危险，
因为养殖户会读正文。

因此 `orchestrator._report_from_parsed()` 的规则是：模型复述的等级与融合层不一致时，
判定它**误读了输入**，整份输出作废、退回规则模板（`_fallback_advisories()`），
并在 `trace` 记一条 `guardrail` 轨迹、写进 `degraded_reasons`，**绝不静默覆盖**。
告警标题集合不一致则按融合层回填并留痕。

### 8.5 提示词工程原则（保留）

结构化数据用文本块注入而非自然语言拼接；输出经 Pydantic 校验；
正反例对照内嵌在提示词里；提示词随代码一同纳入版本管理。

### 8.6 实施同步：提示词双语与回译层（D12）

> 决策 D12 定为 **A. 英文 prompt + 结果回译**。`KurmaAI/AQUA-7B` 是
> `Mistral-7B-Instruct-v0.3` 的英文微调（HuggingFace 标签 `language: en`），
> 让它直接写中文，质量没有任何保证。

#### 8.6.1 提示词从 4 个常量变 8 个

| 中文版（新增前就有） | 英文版（本次新增） |
|---|---|
| `DOMAIN_CONSTRAINTS` | `DOMAIN_CONSTRAINTS_EN` |
| `SCHEDULER_SYSTEM_PROMPT` | `SCHEDULER_SYSTEM_PROMPT_EN` |
| `ADVISOR_SYSTEM_PROMPT` | `ADVISOR_SYSTEM_PROMPT_EN` |
| `ADVISOR_USER_TEMPLATE` | `ADVISOR_USER_TEMPLATE_EN` |

两个渲染函数改为**接受 `lang` 参数**：`build_scheduler_context(ctx, lang="zh")`、
`build_advisor_user_message(..., lang="zh")`；新增 `prompt_lang_for_provider(provider)`。

**唯一的语言例外**：`risk_level` 的取值仍然是**中文枚举**（"正常"/"预警"/"高危"），
英文提示词里也照抄这三个词。理由是它同时是护栏要比对的**标识符**——让模型
翻译它等于让护栏失效。

英文版不是逐字翻译，而是**按母语习惯重写**，并补了三处对英文模型特别重要的说明
（中文版因为语料本身是中文而不需要）：溶氧的昼夜节律要用 `02:00–06:00` 这种
24 小时制讲清、病害结果必须比对 `"健康"` 这个中文字面值、动作长度上限按
**英文词数**给而不是按汉字数给（中英文的字数/词数不可比）。

#### 8.6.2 回译层（`src/fisheries/agent/translate.py`）

```
数据 ─► 英文提示词 ─► AQUA-7B 英文作答 ─► back_translate_report() ─► 中文报告
```

三条硬约束：

1. **只碰"话怎么说"，碰不到"风险几级"。** `risk_level` 与 `alerts` 不过翻译
   （`TEXT_FIELDS` 不含它们）——它们分别是护栏比对用的标识符与融合层的确定性结论。
2. **译不出来就退回规则模板的中文表述，绝不保留英文。** 半英半中的报告比
   少一句建议更糟。每一次退回写进 `BackTranslation.notes` → `degraded_reasons`。
3. **回译模型挂掉不能拖垮整条链路。** 调用异常/超时/返回不改写都不抛异常，
   只降级并上报。

四级后端按可用性自动降级（`FISHERIES_TRANSLATOR_MODE`，默认 `auto`）：

| 后端 | 启用条件 | 能力 |
|---|---|---|
| `local` | **有本地模型时优先**（离线、零 key、确定性） | 整句翻译；分块限长 + 术语后订正，见 8.6.4 |
| `llm` | 没本地模型，但配了 `FISHERIES_TRANSLATOR_*`，或调度角色有可用模型 | 整句翻译 |
| `glossary` | **兜底**；离线、确定性、零依赖 | 短句/指标名直译；整句英文一律拒绝 |
| `bypass` | 显式指定 | 保留英文，**只用于调提示词** |

**为什么"没配翻译模型就复用调度角色的模型"**：D12 的前提是"AQUA-7B 用英文
思考、另一个中文模型负责回译"，而推荐部署里调度角色本来就是中文强模型
（DeepSeek/Qwen）。不借用它，用户得把同一个 key 配两遍，忘了配就静默退化成
词表回译、白丢 AQUA-7B 的整句输出。本地后端（ollama/vLLM）不需要 key；
provider 配了但没 key 的"注定失败的调用"在构造阶段就挡掉，不留到运行时空等超时。

#### 8.6.3 词表回译为什么拒绝整句

`GlossaryTranslator` 有一个 `max_words` 上限（默认 6）。逐词硬译
`"Dissolved oxygen is about to crash. Turn on the aerator now."` 会得到
"溶解氧 是 关于 到 崩溃 打开 在……上 这 增氧机 现在"，那比退回模板更糟。
所以它只做短句与名词短语（`timing`、`target`），超出上限直接拒绝并退回模板。

**这个上限曾经让 D12 的收益变成名义上的**：AQUA-7B 产出的自由长句必然超过
6 词，于是整句被拒 → 退回规则模板 → 模型的输出一个字都没进报告；而离线机器
没有远端翻译模型，`auto` 必然落到词表后端。也就是说**旧的 `auto` 在没有
API key 的机器上，D12 的收益恰好等于 0**。

改法是补一个**本地离线 NMT**（8.6.4），把它放在 `auto` 的第一位。
量化对照（同一份报告逐字段回译）：

| 后端 | `n_translated` | `n_replaced`（被模板替换掉的字段数） |
|---|---|---|
| `glossary`（旧的离线默认） | 1 | 4 |
| `local`（现在） | **6** | **0** |

#### 8.6.4 本地离线翻译模型 + 分块 + 后订正

**选型**：`Helsinki-NLP/opus-mt-en-zh`（Marian 专用英中 NMT，约 77M 参数，
CPU 单句 0.3–0.7 s）。需求里提到的 `qwen-translate` **不是一个真实存在的
可下载模型名**；实际可选的是专用 NMT 或 Qwen 小号通用 instruct。
权重不在 PyPI 上，由 `scripts/fetch_translate_model.py` 下到
`models/translate/`（优先 ModelScope，备用 `hf-mirror.com`），约 315 MB。
依赖放进 `pyproject.toml` 的 `[translate]` extra，且**全部惰性 import**——
没装时 `import fisheries.agent.translate` 照常成功，只是退回词表后端。

**为什么必须分块**：模型一次吞下整段英文会**把尾部整段丢掉**。标尺句
`"Turn on the aerator tonight and measure dissolved oxygen and ammonia nitrogen
again tomorrow morning at 6."`（106 字符 / 17 词）在 200 字符 / 40 词的预算下
输出 `今晚打开气动器 测量溶解氧气和氨氮`——`at 6` 连同数字 6 一起没了，
数值校验只能把整条字段放弃。逐档实测：

| 字符预算 | 词预算 | 切出块数 | 数字 6 |
|---|---|---|---|
| 200 / 140 / 110 | 40 / 28 / 20 | 1 | ✘ 丢 |
| 90 / 70 / 55 | 16 / 12 / 9 | 2–3 | ✔ 保住 |

**词预算才是那条线，字符预算不是。** 取 `DEFAULT_CHUNK_CHARS = 110` /
`DEFAULT_CHUNK_WORDS = 16` 而不是更小，是因为切得越碎模型越容易把术语译错
（`quicklime` 在预算 200 时→"生石灰"，预算 70 时→"快生石灰灰"）。
预算是**重试触发器**而非固定开销：预算内的短句仍是一次调用，延迟与质量零变化。
硬切不会切在数字与单位之间（`_glue_number_units`）。**任一块失败 ⇒ 整条字段放弃**，
不做半英半中。

**为什么还要后订正**：通用 NMT 不懂水产，语序对、术语全错。实测错法
`turbidity`→"多发性"、`bacterial gill disease`→"细菌刺痛病"、`aerator`→"呼吸器"、
`stocking density`→"丝袜密度"、`NTU`→"纽芬兰先令"、`zeolite`→"佐利特"。
词表后端的失败正好相反（词认得、语序拼不出），**两者互补**——所以让 NMT 负责
语序、让词表负责术语：NMT 先出通顺中文，再用一张中文→中文的后订正表
（`GLOSSARY_POST_ZH`）把术语扳回来，最后 `normalize_units()` 把单位收回
`mg/L` / `μg/L` / `℃` / `ppm` / `NTU` 并补空格。

两个实现细节值得记下来：

- **收录标准是"本领域里不可能有第二种解释"**。`措施`（measure 会被译成它，
  但"采取措施"是正当中文）、`发病率`（本身是正当的病害统计词）、`中度`
  （"中度污染"是正当中文）**故意不收**，理由写在代码 docstring 里。
  这类错法是**开放集合**，换个句子可能又冒一个。
- **替换必须一次扫描、最长优先**（`_compile_alternation`），不能逐条 `str.sub`：
  表里有 `亚硝酸 ⊂ 亚硝酸盐`，逐条替换会把刚改好的结果切回一半。
- **"最长优先"还不够，正确写法本身也要占位。** 交替正则匹配的是*输入*，
  而 `亚硝酸盐` 自己不是键，于是输入的 `亚硝酸盐` 被 `亚硝酸` 吃掉前三个字、
  补一个 `盐`，得到 **`亚硝酸盐盐`**。修法是给 `亚硝酸盐` 补一条恒等规则
  让它整体被消费。这个缺陷是补测试时才抓到的（文档里早写了断言，代码里
  却没有测试守着），所以顺手补了一条**通用不变量**：对表里每一条 `(k, v)`
  都要满足 `fn(v) == v`——以后加规则会被自动检查。
  见 `tests/unit/test_translate.py::TestPostEdit::test_every_replacement_is_itself_stable`。

**已知限制**：各块独立翻译再拼接，跨块的指代与连接词会失真（实测输出
`今晚打开增氧机测量溶氧明天早上6点再有氨氮和氨氮`，多出一个"再有"）；
`opus-mt-en-zh` 是 2020 年前后的 NMT，中文自然度不如现代大模型，
它的价值是**离线、确定、零 key**。

完整实测数据、复现命令与全部已知限制见 `docs/M10_回译层说明.md`。

### 8.7 实施同步：可信度说明改为「规则算事实 + 模型照模板措辞」

**背景（负责人指令 m03844）**：`confidence_note` 原先有两种写法——规则模板路径写死
一句「本建议由规则模板生成，仅供参考」，LLM 路径则由模型自由发挥。前者是套话
（读者看不出这份结论哪里硬、哪里软），后者不可靠：评估可靠性需要看到 `trace`、
数据质量、模态失败记录、知识库核对状态，而模型只拿到一小段文本，它写的
「本次结论可靠」是凭印象说的。

**改成两段式**（`src/fisheries/agent/prompts.py`）：

| 阶段 | 入口 | 产出 | 谁负责 |
|---|---|---|---|
| ① 算事实 | `build_confidence_facts(water, vision, fusion, knowledge) -> dict` | 扁平 dict：`water_points` / `water_enough` / `water_extrapolation_hours` / `water_degraded` / `vision_disease` / `vision_confidence` / `vision_low_confidence` / `failed_modalities` / `knowledge_unverified` … | 规则，**不含任何措辞** |
| ② 给模板 | `format_confidence_block(facts, lang) -> str` | 已填好事实的三栏 + 「句式固定为：依据：…。不确定：…。复核：…。」 | 写进 advisor 提示词 |
| ③ 出成品 | `render_confidence_note(facts, lang) -> str` | 同一份事实渲染的成品句，供规则模板路径与回译兜底 | 规则，与 ② 同源 |

常量：`CONFIDENCE_CLAUSES_ZH = ("依据", "不确定", "复核")`、
`CONFIDENCE_CLAUSES_EN = ("Evidence", "Uncertainty", "Review")`。

**三条设计决策及理由**

1. **三句式固定，不自由发挥**。可靠性说明的价值在于「读者能一眼看出哪一栏
   有内容、哪一栏空着」，自由格式会让这两件事都变得不可比。
2. **「不确定」与「复核」由同一份事实推导**。图像分析失败时，
   前者说"这份结论里没有图像证据"，后者说"请人工重做图像分析"——
   拆成两套规则一定会出现「说了不确定却没说该怎么办」。
3. **空栏必须显式写死**：「无明显不确定项」「无需人工复核」。
   留空读者会以为我们忘了写，而"没有已知不确定项"和"没算"是两件事。

**诚实边界**：这一栏仍然**不由模型决定内容**，模型只决定措辞的丰富度。
它能写「水质 24 点，趋势判断扎实，但结论含 12 小时外推」，不能写
「本结论可靠」——后者没有出处。模型漏写这一栏时回填
`render_confidence_note(facts)`，而不是在报告里留一个空栏。

**跨语言**：英文路径独立成句（`Evidence: … Uncertainty: … Review: …`），
疾病名走 `DISEASE_LABELS_EN` 映射。D12 的前提是英文底座用英文思考，
素材再给中文等于先让它做一次阅读理解的翻译。

## 9. 后端接口设计

|---|---|---|---|
| `/api/v1/health` | GET | — | 各工具/模型可用性、版本 |

## 10. 前端（原计划 Streamlit → 最终实施为零依赖原生前端）

### 10.1 原计划

| 页面 | 功能 |
|---|---|
| 首页 / 总览 | 项目介绍、架构图、当前池塘状态卡片 |
| 水质分析 | 上传 CSV 或选示例数据 → 清洗过程可视化 → 趋势图（matplotlib）→ 风险等级与告警 |
| 病害识别 | 上传鱼照片 → 预测类别 + 置信度 + 概率分布条形图 + 处置方案 |
| 融合评估 | 同时提交水质与图片 → 展示融合推理链与升级原因（**答辩重点页面**） |
| 知识问答 | 对话式提问 → 回答 + 引用来源 |
| 数据与标准 | 阈值表格、数据集说明、引用标准 |

原选 Streamlit 的理由：纯 Python、一键启动、录屏与截图方便、演示崩溃风险低。
QQ 机器人作为可选拓展，不作为主演示路径。

### 10.2 实施同步：改为零依赖原生前端 + 同源托管

前两轮方案（Streamlit → Gradio 单页）都已作废。最终实现是 `web/` 下的一套
**纯原生 HTML / CSS / JS**：无构建步骤、无打包器、无 CDN、断网可演示，
由 `src/fisheries/api/static.py` 挂到接口进程的 `/app`。三条理由：

1. **同源托管消掉演示现场最容易出问题的一环。** 页面与接口同一个进程、同一个端口：
   不用配 CORS（跨源预检会被演示机上的代理与安全软件拦掉）、不用手改基地址、
   只有一条启动命令。挂载点选 `/app` 而非 `/`，是把 `/` 留给机器可读的服务目录 JSON、
   `/docs` 留给 Swagger。找不到 `web/` 时 `resolve_web_dir()` 返回 `None`、接口照常启动——
   只拷 `src/` 的部署不该因为缺静态目录就起不来。
2. **没有构建步骤，就没有「现场编译失败」这一种故障。** 改完刷新即生效，也不需要 Node 工具链。
3. **去掉一个大依赖。** Gradio 与 `src/fisheries/webui/` 整个目录已删除；
   `pyproject.toml` 的 `webui` extra 换成 `api` 与 `rag` 两个 extra。

### 10.3 四个视图

| 视图 | 路由 | 内容 |
|---|---|---|
| 总览 | `#/home` | 后端状态卡、塘口历史风险趋势（0–100，画 40 / 70 两条参考线）、降级横幅 |
| 智能评估 | `#/evaluate` | 选内置模板或上传表格 + 鱼体照片 → 完整报告（**主入口**） |
| 知识问答 | `#/qa` | 直接问知识库，返回召回片段、出处与「未核对标准原文」标记 |
| 数据与标准 | `#/standards` | 阈值表、品种档位、红线、两个工具的调用契约 |

文件职责：`index.html`（骨架）/ `css/app.css`（全部样式）/
`js/app.js`（路由 + 四页交互）/ `js/api.js`（接口客户端，12 个端点）/
`js/parse.js`（表格解析）/ `js/dict.js`（枚举字典）/ `js/ui.js`（报告渲染）/
`js/charts.js`（零依赖 SVG 图表）/ `js/markdown.js`。

### 10.4 三条硬约束：前端绝不自己算

- **等级与分数只读后端。** 页面不做任何阈值比较，`risk_level` / `fused_score`
  一律原样显示；`tests/unit/test_web_contract.py` 会扫描 `web/js/` 是否出现
  `risk_level =` / `fused_score =` 这类赋值。
- **枚举码必须与后端源码对齐。** `dict.js` 里的红线码 / 规则码 / 融合码 / 轨迹类型
  是「前端认得的码」的唯一真相。这一条踩过坑：`REDLINES` 曾多了两个后端永远收不到的键、
  漏了三个真会发的码，界面上于是直接显示英文码。契约测试因此**直接 `inspect.getsource()`
  读后端函数体取真值，不在前端再抄一份**（抄一份的结果是两边一起错、且错得一致）。
- **不显示服务器路径。** 图片预览走本地 `objectURL`，`stored_path` 从不渲染。

### 10.5 数据接入层为什么不能省（`src/fisheries/tables.py`）

实测数据集里同一个指标至少有四种列名写法（`Dissolved Oxygen(g/ml)`、
`DISOLVED OXYGEN`——拼写错、`PH`、`Ammonia(g/ml)`）。把原始 CSV 直接喂给
`water_risk_predict` 只会得到 pydantic 校验错，演示时看起来就是「系统坏了」。
因此这一层承担四件事：**精确别名匹配**（不做模糊匹配——
`Total_Phosphorus_mg_L` 含 `ph`、`Nitrate` 与 `Nitrite` 只差三个字母，
模糊匹配会把列认错）、**时间轴解析与重排**、**设备哨兵值 `-127`/`-999` 按缺失处理**
（否则「水温 -127℃」会直接顶到危险档）、**量纲与非有限值核查提醒**。

两条关键实现约束：

- **必填格缺失时丢整行，而不是留一个 `None` 键。** 留 `None` 会让**整个请求**
  被 pydantic 拒绝，用户看到「工具调用失败」，而真实原因只是某一格是空的。
- **补插时间戳必须只动缺失行。** `water_risk._resolve_interval` 要求**所有**点
  都有时间戳才肯用时间戳推断间隔，否则整体退回 `interval_minutes` 入参，
  趋势外推的时长含义就错了。但补插若按「首点往后每步加一个间隔」铺，
  补出来的点会抢走真实时间戳的位置，把后面所有实测点的时刻整体推后一格。
  正确做法是**按相邻已知点的行序线性内插**。

### 10.6 依赖边界

前端**零第三方依赖**（原生 JS，由接口进程托管）。
`web/js/parse.js` 与服务端 `src/fisheries/tables.py` 是两份职责相同的解析实现
（前者用于离线粘贴 / 拖拽，不必先发请求）；**改一处必须同步另一处**，
而 `tests/unit/test_tables.py` 只钉服务端这一侧。

界面默认走离线 MockLLM + 规则模板建议，与命令行 demo 同一条链路；
配置真实模型后页面会自动显示当前后端。

## 12. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 数据处理 | pandas, numpy, scikit-learn | 负责人已熟悉，比赛文档一致 |
| 时序模型 | TensorFlow/Keras LSTM（负责人交付），备选 TCN / LightGBM | 轻量、普通笔记本可训练 |
| 图像模型 | YOLOv8-cls（ultralytics） | 迁移学习，训练快；与"YOLO"需求表述一致 |
| 后端 | FastAPI + Uvicorn | 自动生成 OpenAPI 文档，便于答辩展示接口 |
| 数据契约 | Pydantic v2 | 校验 + 序列化一体 |
| 向量库 | Chroma（首选）/ FAISS | 本地持久化，离线可用 |
| LLM | DeepSeek API（首选）/ 通义千问 | 中文效果好、成本低；预留 OpenAI 兼容接口 |
| 前端 | 原生 HTML/CSS/JS（原计划 Streamlit → 曾用 Gradio → 最终零依赖原生页面） | 无构建步骤、无 CDN，由接口进程同源托管在 `/app`：不用配 CORS、不用手改基地址、只有一条启动命令。见 §10.2 |
| 测试 | pytest + pytest-cov | 标准方案 |

### 13.2 实施同步：M8 外部验证（两组，见 `docs/M8_评测报告.md`）

这一节改过两轮，先说结论怎么变的：原计划只写"用 WQI 分级标签做外部验证"，
执行时发现那条真值不可用，于是补了第二组；再后来**两组数据整体换掉**——
因为前两轮用的都是**地表水断面监测**，而引擎是按**池塘养殖**阈值设计的。

#### 第一轮（已停用）：污染分级标签——负结果，真值不可用

在主口径（映射 A、趋势窗口 3）上跑了 2640 个样本（180 个监测站、2023 全年），
准确率 31.9%、Cohen's κ -0.011、Spearman ρ -0.028。这三个数字接近随机，
但诊断表明原因不在引擎：对数据集**每一个数值列**算与标签严重度的 Spearman ρ，
结果 **|ρ| 全部 < 0.03**，其中包含数据集**自带的** `Water_Quality_Index`（ρ -0.029），
且每个五级标签下的测量值分布完全一致。

结论：**这次评测既没有证实也没有证伪引擎**，31.9% 不能读成"引擎准确率"。
产出不是指标，而是两条：① 一条关于数据集的确定结论（标签与测量值统计独立），
② 引擎在真实量级数据上 2640 次调用 0 失败、单次 0.12 ms 的工程证据。

> **新增的实施纪律：拿到带标签的数据集，先验证标签，再谈模型。**
> 原计划选它的第一条理由是"标签是现成的"——"现成"不等于"可用"。
> 这条纪律的可执行形式当时是 `evaluation/label_signal.py`；
> 换成池塘数据后它被**删除**了——不是纪律被放弃，而是新数据的标签是**我们自己按阈值现算的**，
> 没有"标签是否可信"这一问，取而代之的是下面 `labels.growth_coherence` 那条**不依赖自建阈值**的自洽性检验。

#### 第二轮（已停用）：河川溶氧回归真值——有真值，负面但可量化

144 条真实河川溶氧序列上，比较引擎的线性外推（`末点 + 最小二乘斜率 × 一步`）
与持久性基线（`下一个值 = 当前值`）：引擎 MAE 2.719、基线 MAE 1.638，
**劣于基线 66.0%**，方向判对率 26.4%。历史点越多越接近基线（2 点时 -91%、7 点时 -14%）。

停用理由有两条：**河川断面的溶氧动力学与静水养殖塘不是一回事**（引擎的"3 小时内骤降 2.0 mg/L"
这类判据在宽表上无从触发），且那份宽表的 7 个滞后列**没有绝对时间单位**，
"一步"是多长只能假定——而池塘数据带真实时间戳，这个假定可以去掉。

#### 第三轮（现行）：两组都跑在池塘实测数据上

- **数据**：`aquaponics_pond`（`Sensor Based Aquaponics Fish Pond Datasets`），
  11 个 CSV / **1,114,970 行** / 2021-06-18 ～ 2021-12-30 / 原始采样间隔中位数 **20 秒**。
  这是**真·时序**——每条塘有上万条连续读数，所以第一轮那个"复制读数凑 `min_length=3`"的
  **瞬时口径妥协整个消失了**。
- **标签不再是数据集给的**。改用 `water_risk.py` 的 `SPECIES_PROFILES["鲤科"]` 与 `REDLINE`
  **现算**三档（正常 / 预警 / 高危），口径是**最差指标决定论**（`evaluation/labels.py` 的 `AQUA_BANDS`：
  任一指标越红线即高危，任一指标出适宜带即预警）。样本按 10 分钟聚合、3 小时滑窗、**步长 = 窗长**。
- **外部验证一（阈值定级，⚠ 标签不独立）**：3,183 个不重叠窗口上准确率 72.2%、
  Cohen's κ 0.573、ρ 0.786、漏报率 0.0%、误报率 19.8%、红线召回 1123/1127（99.6%）、
  主控因子一致率 1644/1907（86.2%）。标签与引擎是**同一套阈值**：标签取最差指标（最坏情况），
  引擎取加权评分 + 时间持续性（平均 + 趋势）——所以它量的是**两套口径的分歧**，不是与事实的符合度。
- **外部验证二（溶氧外推，✅ 真值独立）**：8,198 个样本、回看 18 点（3 小时）预测 1 小时之后的
  真实溶氧：引擎 MAE **1.943** vs 持久性基线 **1.696**，**劣于基线 14.5%**，方向判对率 44.1%。
- **量纲推断（必须写进报告，因为它可被推翻）**：数据列名标 `Ammonia(g/ml)` / `Nitrate(g/ml)`，
  但按字面读会得出"鱼在致死浓度里增重 120 倍"的矛盾（同一份数据里记录了体长体重，
  IoTPond7 体重 8.0 → 998.5 g），故按 **µg/L ÷1000** 处理；唯一标 `(mg/L)` 的 IoTPond8 不换算，
  量级恰好是其余文件的 1/1000，是最强旁证。溶氧（中位数 3.3～18.3）不换算。
  换算系数与量程表是 `evaluation/ponds.py` 的 `UNIT_DIVISORS` / `RANGES` 两个**可改常量**。
- **一个真实盲区**：这份数据只有硝酸盐、**没有亚硝酸盐**，引擎的一级指标 `nitrite_n` 填不进去，
  权重被重新归一化——真实塘口亚硝酸盐超标时本评测看不到。
- **一条不依赖自建阈值的检查**：11 口塘的"高危样本占比 vs 鱼体重增长" Spearman ρ = **-0.582**。
  这条检验用的是**塘口事实**（鱼长没长），不是我们算的标签，是唯一能说明"标签没荒谬到反着来"的证据。

#### 刻意的实现选择（理由）

① 外推那条口径**直接调用 `water_risk._slope_per_hour`**（同一个私有函数）而不是在评测里重写一遍最小二乘
——否则量的是"我复现的算法"，不是"线上跑的那段代码"；
② 评测子包**不参与线上链路**（`fisheries.evaluation` 单向依赖 `fisheries.tools`），
删掉它不影响任何生产行为；
③ 评测代码自身也要被测——`tests/unit/test_evaluation.py` 钉住阈值分档、混淆矩阵与 κ、Spearman、
滑窗切分、**量纲归一与量程清洗的先后顺序**、生长自洽性，且**不读那 96 MB 真实数据**（用合成 CSV）。
**评测代码算错比引擎算错更隐蔽**：报告里的数字会看起来很有信息量。
这一轮就抓到一个真实缺陷——`ponds.py` 的 `cell()` 一度**先按量程清洗、后做单位换算**，
而 `RANGES` 写的是**归一化之后**的量的量程，于是合法的 µg/L 氨氮/硝酸盐读数被静默当成坏值丢掉，
"清洗掉 1,246,392 个越界值"里有一大半其实是好数据。调换顺序后：越界值降到 384,372、
聚合点从 40,121 升到 49,394、κ 从 0.555 升到 0.573。

#### 限制（已同步进报告与读者可见的文案）

两组数据现在是池塘实测，**但第一组的标签仍不独立**（与引擎同阈值），
所以全篇唯一可以对外引用的性能数字只有第二组那一条。
报告里出现"预计 N 小时后跌破某线"时，**只能读成趋势提示**——第二组已经量化了这条外推的强度。

### 13.3 评测指标

| 对象 | 指标 |
|---|---|
| 图像模型 | 准确率、宏平均 F1、混淆矩阵、各类召回率（**病害类别召回率优先于准确率**，漏检成本高于误报） |
| 时序模型 | MAE / RMSE（DO、氨氮）、趋势方向准确率、风险等级命中率 |
| 融合决策 | 风险等级与专家判定的一致率；红线规则召回率（必须 100%） |
| Agent 整体 | 端到端成功率、平均工具调用轮数、幻觉率（输出数值与工具输出不一致的比例，目标 0） |

### 13.4 数据划分纪律

- 图像：使用官方 `Train / Valid / Test`，**禁止**用 `Train_Augmented` 评估。
- 必须对 `Fish Disease Dataset` 与 `Freshwater Fish Disease Aquaculture in south asia` 做**感知哈希去重**，确认无跨集同源后再用后者做外部验证，否则准确率虚高。
- 时序：按**时间顺序**划分（前 80% 训练 / 后 20% 测试），禁止随机打乱，防止未来信息泄漏。
